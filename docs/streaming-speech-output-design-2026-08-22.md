# AI2Apps Chat 流式语音输出技术方案

日期：2026-08-22
状态：第一阶段已实现，待 Runtime 实机验收

## 目标

当前 Chat 只在整条回复生成完成后，把全文交给 TTS，并等待完整 WAV 返回后开始播放。长回答会同时叠加 LLM 生成时间和 TTS 合成时间，首段语音延迟过高。

目标是让 Chat 在收到若干秒可读文本后立即开始合成和播放，同时继续接收 LLM 文本、合成后续语音。停止生成、切换会话、再次点击朗读或发生错误时，所有未完成的合成和播放都必须可取消。

## 第一阶段：语句流水线

第一阶段复用现有 `POST /v1/audio/speech`，不要求当前 TTS Package 支持原生音频 chunk：

1. Chat 从 SSE 文本增量中识别句号、问号、感叹号、分号和换行等强边界。
2. 长时间没有强边界时，在逗号等弱边界或长度上限处切分，保证首段不会无限等待。
3. 每段使用现有 TTS 接口独立合成为 WAV。
4. 合成队列单线程执行，避免同一模型并发推理；播放队列严格保持文本顺序。
5. 第 N 段播放时允许第 N+1 段合成，实现 LLM、TTS 和音频播放三段流水。
6. 最多缓存两个已合成但尚未播放的 WAV；达到上限时暂停后续合成，形成浏览器侧背压。

```text
LLM SSE ──> 增量分句 ──> TTS 合成队列 ──> WAV 就绪队列 ──> 顺序播放
   │              │              │                  │
   └──继续生成────┴──继续入队────┴──预合成下一段────┘
```

### 分句策略

- 强边界：`。！？!?；;` 和换行。
- 弱边界：`，,、：:` 和空白；缓冲达到约 24 个可读字符且短暂停顿后允许提交。
- 硬上限：约 56 个字符，优先回退到最近弱边界。
- 提交前删除 Markdown 标记、链接地址和代码围栏，避免朗读格式控制字符。
- 流结束时提交剩余尾句，即使没有终止标点。

这些阈值是体验参数，不属于 Package 能力，后续可根据中文、英文和模型实时率调优。

### 状态与取消

每次朗读创建独立 Pipeline，持有：分句缓冲、合成 Promise 链、播放 Promise 链、`AbortController`、当前播放器和完成状态。

以下事件会终止当前 Pipeline：

- 用户停止当前 LLM 生成；
- 用户再次点击正在朗读的消息；
- 开始朗读另一条消息；
- 切换或新建会话；
- 工具调用使当前可见草稿失效；
- TTS 请求或播放失败。

终止时中断网络请求、暂停播放器、释放 Object URL，并通过 Pipeline 身份检查阻止旧异步任务恢复播放。

## Runtime 与 Package 协议

第一阶段不改变 `/v1/audio/speech` 协议，也不要求模型 Worker 升级。当前 Package 即使只支持完整 WAV，也能按短句参与流水线。

部署仍需要发布 Runtime Package，因为 Chat 模板和静态分句模块随 Runtime 分发。

第二阶段可为真正原生流式 TTS 增加以下能力：

- Package 声明 `audio_capabilities.streaming.mode: native`；
- Worker 使用 `ModelWorkerStream` 输出 PCM/音频 chunk；
- Runtime 代理背压、取消和音频格式协商；
- Chat 在浏览器支持可靠的流式 PCM 播放时，按 capability 自动切换原生模式；否则继续使用语句流水线。

这能减少单句内部延迟，但不是第一阶段获得主要体验收益的前置条件。

## 验收标准

- 自动朗读在完整回答结束前开始播放。
- 含多个句子的回答严格按原顺序播放，无重叠、无漏段。
- 问句保留问号并作为强边界及时提交。
- 无标点长文本仍会在长度/空闲阈值处开始播放。
- 停止生成后不再启动任何排队语音。
- 工具调用递归不会朗读已丢弃的中间草稿。
- 手动朗读继续可用，并复用相同的分句、预合成和取消机制。
- TTS 失败只显示一次明确错误，不影响已生成的聊天文本。

## 后续指标

本地端到端验证记录首 token、首可读句、首音频和播放结束四个时间点。第一阶段重点关注“首可读句到首音频”的延迟，以及持续播放时的断续次数；随后再决定是否需要原生 Worker 音频流。
