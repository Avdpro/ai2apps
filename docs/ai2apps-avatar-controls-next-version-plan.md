# 数字人下一版开发计划：转头、注视与情绪控制

日期：2026-10-01。状态：`planned`，用户已确认纳入下一版；本文是开发计划，尚未实现或发布这些控制能力。

## 1. 目标与发布基线

让 App/Mini-App 用统一语义描述“看哪里、如何转头、以什么表情说话”，由 Host 与模型适配器执行。切换兼容模型时无需修改 App；不同模型的控制能力和精度必须明确展示。

当前发布基线：AVTR-1 0.1.0、FlashHead 0.1.0（Lite/Pro）、EchoMimic 0.1.2、Avatar Studio Suite 0.1.2，Repository Snapshot 232。现有 Runtime 1.8.5 已满足这些模型的安装推理需求。通用原图“裁剪—生成—回贴”已完成开发验证，仍待随 Desktop 更新交付。

## 2. 下一版范围

### 2.1 转头与注视

必须交付的离线能力：

- 小幅左右转头、抬头/低头和歪头，支持保持姿态与平滑返回。
- 看镜头、看最终画布中的指定位置；头部和眼睛可以联合控制。
- 按时间轴指定“看向图表—停留—看回观众”，支持多段关键帧。
- 保留可调强度的自然头动；明确处理自然动作与人工控制的冲突。
- 在现有任意尺寸回贴流程中保持目标坐标一致，不把裁剪坐标暴露给 Mini-App。

用户位置追踪纳入本版独立实验里程碑：完成摄像头用户位置估计、目标方向映射、控制平滑和持续渲染原型。达到实时门槛后才作为正式功能开放；若未达到，记录瓶颈与测量结果，离线功能仍可独立交付。不能把离线生成、循环播放或官方 CUDA 的性能当作本机实时追踪验收。

### 2.2 表情与情绪

必须交付：

- 直接表情控制：微笑、眉毛变化、眼睛开合、眨眼；分别提供强度和时间范围。
- 首批情绪预设：中性、友好、严肃、疑惑、惊讶。预设是经过验证的表情/动作组合，不宣称模型理解了情绪。
- 同一条音轨上叠加适度表情，保持口型、人物身份和音视频同步。
- 对不支持的控制明确报错或在执行前要求选择兼容模型，不静默忽略。

后续扩展：悲伤、愤怒等更复杂的情绪，多种情绪混合，以及与 TTS 的情绪语音联动。已有音轨的语气不会因面部情绪参数而改变；文本生成链路应先合成语气一致的音频，再生成数字人。

本版不包含人物抠像（由 Composer 提供）、大角度侧脸重建、全身动作、手势生成、多人互动或完整 ASR/LLM/TTS 对话系统。点头/摇头可复用姿态轨道，作为后续预设，不阻塞首版。

## 3. 模型路线

| Provider | 本版工作 | 当前边界 |
| --- | --- | --- |
| AVTR-1 MLX | 首个直接控制 Provider；在运动生成与渲染之间加入姿态、眼神、表情混合 | 已有旋转与面部运动表示；控制映射和效果尚未验证 |
| LivePortrait | 参考上游的头部/眼球/表情编辑实现，核对已有 MLX 渲染代码的复用边界 | 上游存在编辑代码，不等于我们当前 Package 已暴露或验证这些能力 |
| EchoMimic V3 | 保留现有生成；验证提示词能否提供可用的情绪倾向 | 有文本条件，不承诺精确角度、目标位置或逐时刻控制 |
| FlashHead Lite/Pro | 保留音频驱动生成，正确声明不支持新增直接控制 | 当前没有验证过的姿态、注视或情绪参数 |

优先在 AVTR 内部修改运动表示后渲染一次。暂不默认对 FlashHead/EchoMimic 成片再跑一遍 LivePortrait；二次处理可能增加身份漂移、闪烁和延迟，若采用须作为独立实验和显式执行计划。

初期复用现有 Runtime，先做纯 Python/NumPy/MLX 的控制映射。只有实测证明需要新增原生算子或依赖隔离时才提 Runtime 变更，不预先建立专用数字人 Runtime。

## 4. 通用控制契约（拟议）

以下名称和结构为待实现草案。先扩展现有 Host/Worker 能力协商与私有桥接，不把它们描述为已经存在的公共 SDK。

### 4.1 能力声明

模型按控制项声明：

- 支持方式：`direct`（直接参数控制）、`prompt_guided`（文本引导）、`unsupported`。
- 支持离线关键帧还是实时更新。
- 参数范围、时间分辨率、混合方式及经过验证的素材限制。
- 支持的情绪预设和强度范围；实验能力单独标记。

`direct` 表示实现路径，不代表角度或眼神达到物理精确度；验收报告另记录误差与效果。App 查询能力决定可用控件，不能硬编码模型名称。

### 4.2 请求结构

建议使用可选控制块 `controls`，包含版本与轨道；无控制块时保持现有行为。示意：

```json
{
  "controls": {
    "schema": "ai2apps.avatar-controls/v1",
    "tracks": [
      {
        "kind": "look_at",
        "subjectId": "host",
        "startMs": 3000,
        "endMs": 5000,
        "target": {
          "space": "output_canvas",
          "x": 0.8,
          "y": 0.35
        },
        "transitionInMs": 350,
        "transitionOutMs": 450,
        "headContribution": 0.4
      },
      {
        "kind": "emotion",
        "subjectId": "host",
        "startMs": 0,
        "endMs": 6000,
        "name": "friendly",
        "intensity": 0.35
      }
    ]
  }
}
```

示例数值仅用于说明字段，不是已验证的控制参数或性能承诺。

拟议轨道：

| kind | 内容 |
| --- | --- |
| `head_pose` | 相对素材初始姿态的 yaw/pitch/roll、自然运动权重 |
| `look_at` | 镜头、画布坐标或经 Host 解析的场景目标；头眼分配 |
| `expression` | 眉毛、微笑、眼睛开合等独立强度 |
| `emotion` | 预设名称、强度与持续区间 |
| `blink` | 指定时刻与持续时间的眨眼事件 |

### 4.3 时间、坐标和冲突规则

- 时间使用相对最终音轨起点的毫秒，Host 按实际帧时间采样；不用帧号绑定某个模型的 fps。
- `output_canvas` 使用最终画布左上为原点、x 向右/y 向下的归一化坐标。超出范围拒绝，不自动猜测。
- Composer 负责解析图表/图层目标在最终画布中的位置；Host 负责坐标变换；模型只接收已解析控制。镜像显示与摄像头镜像必须显式处理。
- 姿态正负方向以人物自身为基准写入契约，并附测试：正 yaw 向人物左侧、正 pitch 抬头、正 roll 向人物右肩倾斜。Provider 映射内部坐标系，不能直接暴露内部旋转向量。
- 摄像头用户位置属于独立的 camera 坐标输入，需要校准/映射后生成注视目标，不能把摄像头像素直接当画布坐标。
- 同一时段的显式姿态与注视头部贡献按固定优先级处理：姿态控制头部，注视优先使用眼睛；超出可达范围必须反馈。明确表情通道覆盖情绪预设的同名通道，不累加到越界。
- 同一通道重叠轨道若没有显式混合策略，规划阶段拒绝。非法数字、超范围、未知预设、超出音轨时长均在推理前处理。
- 控制越界采用“拒绝”或用户明确选择的“限制到已验证范围”；计划返回实际生效值。不能悄悄丢弃控制或改换 Provider。

### 4.4 持久化与兼容性

Host 冻结控制轨道、解析后的目标、混合规则版本、Provider/权重版本和素材摘要；重试沿用冻结输入。旧 Worker 不接收未协商字段，旧 Mini-App 无 controls 请求继续有效。任务结果记录实际生效能力和任何用户接受的降级。

## 5. AVTR 实现设计

现有流程：音频 → 运动预测 → 关键点/旋转 → 渲染 → 原图回贴。

新增流程：音频 → 原始运动预测 → 控制混合 → 关键点/旋转 → 一次渲染 → 原图回贴。

1. 保留原始预测与自回归历史，第一阶段只修改送往渲染的运动，避免控制污染模型历史后产生持续漂移。
2. 在反归一化之后明确姿态与表情坐标系；旋转使用合适的旋转表示和插值，避免直接逐分量线性混合导致跳变。
3. 眼球方向先参考 LivePortrait 编辑实现，按当前 AVTR/渲染器的关键点语义重新标定。眨眼与注视互相协调，不能把眼睛开合当成眼球方向。
4. 表情分通道混合。限制嘴角和唇部修改的强度，保留音频驱动闭唇、张口等关键事件；复杂表情若显著破坏口型则不进入首批预设。
5. 所有控制按绝对时间插值，跨 5 帧运动块连续。姿态保持、停止控制和回到自然动作均有可测试的过渡。
6. 人物特征缓存继续复用；不在每帧重复人脸检测、图像编码或模型加载。
7. 回贴区域预留动作边界，检查头发、耳朵、下巴和颈部。原图中未被覆盖的旧头部轮廓可能在转头时露出，不能仅靠增加羽化宽度掩盖；出现此问题应缩小允许角度或调整经验证的融合区域。

## 6. Host、Mini-App 与 Composer 分工

- **Host Avatar 层**：能力协商、轨道校验、时间/坐标转换、冻结执行计划、取消和重试。
- **Model Worker**：把统一控制映射到模型运动与渲染，不访问摄像头或 Composer 内部状态。
- **Avatar Mini-App**：方向/注视目标、表情/情绪强度与时间段编辑；依据能力展示控件；继续使用 Host 共享输出。
- **Composer**：提供图层/图表目标位置及时间轴；人物抠像仍由 Composer 素材层完成。本版提供对接契约和集成样例，具体 Composer UI 按其开发流程接入。
- **实时实验 Host**：管理摄像头权限、用户位置估计和临时状态；默认只传位置/置信度给控制层，不把摄像头画面传入 Model Worker。

切换模型若造成控制不兼容，应保留草稿并显示具体不支持项，让用户选择兼容模型或明确移除相应轨道。

## 7. 实时用户追踪实验

先验证一个用户和一个数字人：摄像头位置估计 → 校准映射 → 平滑/死区 → 注视和头部控制 → 常驻渲染 → 连续预览。

- 低置信度或用户离开画面时短暂保持，再平滑看回镜头；不跟随检测噪声抖动。
- 控制消息含单调序号与时间戳；丢弃过期更新，队列有界，慢消费者不积累过时姿态。
- 先分开测试无音频注视渲染和带音频完整生成，不能以前者的速度替代后者。
- 拟议产品门槛：512px、持续 60 秒、稳定 25 fps；控制输入到可见画面的 p95 延迟不超过 200ms，首帧准备时间单列。门槛是目标，当前尚未达到或证明。
- 若达不到门槛，保留实验开关和测量报告，不默认出现在正式 Mini-App 实时入口。

## 8. 里程碑与验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| M0 基线与契约 | 控制 schema 草案、坐标示意、能力矩阵、固定测试集 | 明确现有/拟议能力，无控制请求兼容；真实 Package 基线可复现 |
| M1 姿态与注视 | AVTR 小幅转头、看镜头/目标、平滑过渡 | 方向一致、到达/保持/返回正确，跨块不跳变，无明显双眼失配与旧头部残影 |
| M2 表情与情绪 | 直接表情通道、首批五种预设 | 盲看可区分主要效果，强度变化合理，闭唇等口型事件保留，无持续身份漂移 |
| M3 产品接入 | Mini-App 控件、Host 协商与冻结、Composer 对接样例 | 模型切换不静默丢参数；取消/重试保持控制；共享输出和拖拽输入回归通过 |
| M4 实时实验 | 摄像头追踪、常驻会话、低延迟预览 | 报告端到端 p50/p95、fps、内存和掉帧；达标才开放产品入口 |
| M5 发布 | 签名 Package、安装验收、Desktop 台账与回执 | 干净实例通过安装/运行/停止/重启/卸载，双源权重与协议元数据有效 |

测试集至少覆盖 6 张肖像（正脸、轻微侧脸、眼镜、不同发型与光照）、横/竖/方画布、偏置人物和透明输入；使用 2 秒、10 秒、60 秒音轨覆盖短片、段落和跨块持续生成。

- 几何：先以 yaw ±5°/±10°、pitch ±5°、roll ±5°做测试网格；这些是实验目标，不是承诺的安全范围，最终限值由逐素材验证确定。
- 注视：镜头与画布四象限，目标切换、人物位置改变和镜像处理；人工检查眼神，必要时辅以估计器，不能只验证内部参数数值。
- 表情：中性/半强度/全强度，并包含闭唇音、张口音、停顿和眨眼重叠；对照无控制成片检查口型、闪烁和身份。
- 零控制：相同权重、seed、音轨、预设下与基线比较；精确模式应保持原路径，近似模式沿用原数值误差标准。
- 性能：相同素材和预设下，分别记录冷启动、稳态运动/渲染/回贴耗时、内存与首帧时间。目标是新增控制使稳态耗时增加不超过 10%；不得通过降低分辨率或帧率隐性达标。
- 回归：旧请求、能力拒绝、参数边界、时间插值、取消、冻结重试、模型切换和 Host 输出归属。首次映射验收必须运行真实权重与已安装沙箱，不以 mock 或源码方式替代。

## 9. 版本与发布边界

- 暂定 AVTR 与 Avatar Suite 下一功能版为 0.2.0，最终构建前检查 Registry 并固定版本；不提前宣称已发布。
- FlashHead/EchoMimic 仅在适配器或签名能力声明确有变更时升版。提示词情绪控制只有通过 M2 相应验收后才标为可用。
- 新功能需要 Host 更新，不能只发 Mini-App 后让旧 Host 默默忽略控制。发布顺序按真实依赖确定，先确认 Host 契约与 Runtime 能力，再发布模型和 Mini-App；旧 Host 的兼容行为必须验收。
- 不更改已发布制品。沿用现有 Publisher、模型 Package ID、权重协议及来源记录；若无需新权重，不重复上传权重。
- 本计划不要求 Cloud API 改动。如 Registry 需要新增能力投影，先写 Cloud 需求交接文档，不在此仓库修改 Cloud。
- 当前仅完成计划落盘；代码、性能和效果均需按上述里程碑验收。
