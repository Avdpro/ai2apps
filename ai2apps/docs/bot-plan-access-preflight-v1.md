# Bot 延时与重复任务的 Access 预检 v1

2026-11-05，修订 2：系统定时任务、Bot 长期 Access 与可恢复任务清理。首版已实现，本次修正验收记录见 [系统定时任务与 Bot 授权](acceptance/bot-system-schedules-20261105/README.md)（[修订前记录](acceptance/bot-plan-access-20261105/README.md) 保留历史语义）。范围为 Messager 创建及修改的受管 Todo 计划；不改变 Chat、Hook、协作计划的授权协议。

## 2026-11-10 修订：继承 Bot Access

新建或重新审核的 Messager 受管 Todo 计划采用同一套 Bot Access，即时与定时执行使用同一个执行入口。每个 Run 启动时捕获当前有效的 App、Mini-App 与有向 Bot 授权。已准入 Run 的范围不会因后续授权而扩大。调用时复核授权和声明版本。撤销 App 授权会中止旧执行，但采用继承模式的调度在下次启动时使用剩余权限。撤销整项计划仍会停止其执行和调度。

能力发现逐个校验当前 Provider 的 Run 快照和实时授权，复用 App Chat 的点查接口。按需检查可见性时只读取该 Provider，避免反复重建整份权限目录。

计划审核可为 Bot 追加 App、Mini-App 或有向 Bot 授权。追加项保存到 Bot Access。已具备的权限无需重复勾选。运行中遇到未授权的目标时需由 owner 处理。特殊操作仍在原执行交互中逐次确认。

需要另一 Bot 执行的工作通过现有委派能力进入独立子任务。Todo Run 可使用启动时已获授权的接收 Bot。继承模式沿委派分支累加已有权限，新增访问的批准只用于本次根运行。固定计划保留原范围。子任务结果和已绑定产物回到父 Run。父 Run 取消或超时时取消仍在执行的子任务。旧计划保留已审阅的固定或自动授权，重新审核后切换。以下保留旧计划的协议说明。

## 用户流程

Bot 在创建计划前发现可能使用的已安装能力，随任务方案提交 `access_requirements`：能力、明确 Provider（有歧义时必填）、用途、是否为条件分支。宿主验证注册声明，将候选归属到 App / Mini-App，并展示当前已有权限、预计用途、特殊操作。没有提出能力清单的方案必须明确说明预估可能遗漏，不能声称完成了真实 Dry-Run。

确认卡提供两种策略，默认“现在设定，运行时固定”：

- **现在设定**：用户勾选本计划允许的 App / Mini-App，确认后冻结范围。运行中不能增加；Bot 后续获得的全局权限也不会自动加入。缺少权限时停止相关执行，说明缺失，修改并重新确认计划。
- **运行时自动获取**：用户预先勾选允许自动获取的已安装 App / Mini-App 边界。运行中可在该边界内自动获得普通访问，并记录每次执行的权限准入。范围外仍需重新审阅计划；这不是无限授权，也不包括未来安装的 Package。

两种策略均向 **Bot 的长期 App Access** 追加普通目标权限，沿用单开关模型。“现在设定”在确认时保存；“自动获取”在原 Run 选定业务调用、校验审阅范围后保存，浏览目录和打开表单不授予权限。其他已有 Bot 权限保持不变。任务另存冻结的执行范围上限，不作为一套独立于 Bot 的权限系统。删除任务或停用其执行授权不会撤销 Bot 已获得的权限；撤销 Bot Access 会使依赖该授权的旧执行失效。App 与 Mini-App 独立，父 App 不包含子 Mini-App。普通读取、写入和已配置模型用量遵循已有 App 单开关合同；付款、购买、破坏性、敏感、未知副作用及 owner 明确要求确认的操作仍逐项询问。授权不代替参数、归属、账户、模型及预算校验。

确认后反馈任务名称、执行时间、授权策略及已保存结果；后续交互（包括参数表单与 App 交接）回接原 Run，目标必须在已确认快照内，显示任务、当前步骤、待明确参数与原因。用户可继续聊天。可以在任务执行授权列表撤销授权：停止未完成执行、暂停后续调度，保留已完成结果和审计记录。

## 声明预检与边界

预检只读取可信注册表、工具副作用和归属，不调用业务 handler，不试写、付费、启动模型或执行计划来“探路”。`related_capabilities` 只代表相关的条件候选，不解释为必需依赖。最多 16 个显式需求，相关图最多 3 层、48 个 Provider；确认最多 32 个目标、512 个 Provider，授权快照不超过 45 KB；超出时要求缩小范围后再确认，避免保存后才在执行入口失败。没有候选/候选歧义返回明确错误，Bot 重新发现，不猜测目标。

确认卡可展开其他已安装目标，用户可补选。后台短路由修改已有计划时使用最多 128 条、8 KiB 的能力摘要预测新需求；新任务由工作 Agent 通过 app.describe 读取所选完整声明。复用既有模型决策，不为权限预检另外运行模型。动态分支与目录截断可能遗漏需求，这一限制在卡片中公开，不能视为完整静态分析。

每次审阅绑定 actor、Bot、计划版本、原规则、模型、时间及声明快照。快照固定 Provider ID/版本、Tool revision、目标及声明/副作用摘要。即使同一 App 新增能力，也不自动进入已确认计划。Provider、声明或副作用变化需新审阅；Bot 访问 epoch 变化和计划授权撤销均使原执行失效。声明本身不产生授权。

自动模式只在选定具体业务调用的权限准入阶段记录，目录可见性、描述读取和参数表单不产生业务授权准入记录；准入不等于实际调用或业务成功；执行证据仍取原 Tool/Run 的结果。特殊操作只能批准原请求一次，不提供 session/agent/app 扩大范围的选项。不能通过改用另一个 Tool 绕过取消、失败或不确定的副作用。

## 持久化与版本

`messager_task_access_policies` 保存不可变选择及撤销状态；`messager_task_access_leases` 记录原 Todo Run 的目标准入。任务及执行绑定携带 `task_access` 快照，执行时校验原 proposal、actor/Bot、Run 与授权一致。只读 work 投影返回有界审计列表；撤销入口与审批入口同样限制在认证的 Local Desktop 宿主和本人 Bot。

Bot 将调度、执行内容和权限分别提交审阅。仅调整调度或权限时沿用原执行正文。只有用户要求改变每次执行的工作时，Bot 才提交独立的 `instruction_change`，内容限于实际工作变更。宿主不会把对话原文追加到执行正文。

计划修改重新预检、展示原/新规则与权限。确认采用既有 Todo CAS，未来新执行使用新版本；已入队/运行的执行继续原冻结版本。确认中断后使用持久选择和创建回执恢复，不重新取得更广权限。重复审批不能更改原授权选择。未成功应用的孤立 policy 元数据没有执行绑定，不具备执行权。

## 实施与验收

Owner 实现集中在 `messager/task_access.py`、`tasks.py`、`plan_changes.py`、Messager API 和现有确认卡，不在 General 中添加业务名称分支。既有无新协议的历史绑定保留原冻结校验；没有 Read/Write 数据升级逻辑。

验收覆盖：不执行业务的预检、跨 Provider/目标隔离、固定/自动范围、特殊操作原 Run 审批、声明变化、撤销、重复审批、计划 CAS 及旧 Run 快照。使用真实本地 SQLite/Todo/AgentRuntime 与替代模型/handler，付费与真实副作用不属于自动验收。


## 系统定时任务：一个触发时钟

Bot 确认定时任务后仍使用同一个 Todo Task ID 和受管执行绑定，并登记到 `system_task_schedules`，在 Todo → 系统任务 → 待定时执行中显示。日、周、月、小时、定时单次及其时区继续使用 Todo 的统一日历函数；系统 Task 服务通过可信 `next_schedule` callback 推进时钟。`Todo.tick` 排除已登记的任务，不再存在两套触发器。

系统定时或“立即启动”产生系统调度回执，以原 System Task ID 幂等加入既有 Todo 队列，不创建第二个 Agent。实际 AppChat/Agent Run 继续使用原执行、审批和观察器，其系统任务名称取真实 Task 标题。系统目录区分“启动记录 / Dispatch”与实际执行；完成启动记录仅表示入队，不表示业务完成。

系统桥接的 `TodoService.launch(admitted=...)` 仅由可信内部 owner 调用，API、模型及普通 TaskInput 不接受执行快照；actor、原 Task ID、受管执行器及 adapter 授权仍会重新校验，已删除/归档项目不能复活执行。已准入的旧快照允许保留，未准入的时钟必须复核当前 Todo 执行定义，直接修改未审阅说明会停止该时钟。

每个定时槽有持久准入回执，即使调度进程重试也不重放同一槽；调度参数与原绑定冻结。计划修改不重置相同绑定的时钟；已准入系统任务继续原快照，未来新准入使用新版本。停用入口同时关闭源 Todo 计划，恢复、归档和清理不会意外重新开启时钟。重启只修复原目录登记，不补发新的业务调用。

`TaskHandler.next_schedule`、`disable_schedule` 是与 App 身份无关的可信 owner callback，不在共享执行器增加 Bot 名称判断。系统 Task 返回 `cancelled` 时保留该终态，不误记为失败。

## 删除 Bot、清除对话及恢复

- 删除 Bot（或重置）停止其执行、移除系统活动计划，并软删除 Bot 自己创建的后台 Task，保留执行回执和可恢复内容。手动关联的外部/普通 Todo 项目不被当作 Bot 自有任务删除，仍需所属 App 处理。
- 恢复 Bot 时恢复因该 Bot 删除而移除的自有 Task 记录，保留原 Task ID，但状态为暂停、无下次执行时间。旧权限、旧运行、Hook 和定时计划均不自动复活；需重新审阅计划。
- 清除对话确认框独立提供“同时清除记忆”“同时撤销 App Access”“同时删除后台任务”，三个默认均不选。后台 Task 删除为软删除，恢复对话不连带恢复它们，可在 Todo 恢复记录后重新审阅。未勾选时保留任务记录；既有旧上下文执行停止、计划暂停的安全语义保持。
- 删除/恢复、计划停用都不替用户撤销已经完成的外部操作。清除对话并保留 Access 不会丢失之前批准给 Bot 的 App 权限。
