# Messager Bots 开发预览

## 研究 Bot 与创建模板

Messager 在账号第一次打开 Bot 列表时，添加一份内置「研究 Bot」。桌面和手机共用这份 Bot；编辑、拖动或移入「已删除 Bot」后，系统不会覆盖或重新添加它。AI2Apps 通用 Bot 仍是默认会话。

从「＋ → 研究 Bot」创建独立副本。模板预填名称、指南针头像、Role 和已可用的 App 权限，提交前可修改。默认使用 Search All 寻找来源、Web Reader 读取最终页，以及 AI Browser 的网页调查处理站内导航。Role 要求先确认研究对象和范围，按证据给出带编号的引用，并交付已经核实的部分。

「Profile → 填入默认职责」只替换当前草稿，保存后生效。「Access → 恢复默认 App 权限」先列出会启用和移除的项目，再走原有授权校验；它不修改 Role、Bot 协作权限或模型。Mobile 支持从模板创建和编辑 Role；创建后的 App 权限管理仍在桌面。模板更新不会自动改变已保存的设置。

公开论文 PDF 由网页阅读器的 `web.read_pdf` 下载到原会话，再交给现有文档解析器。结果带最终来源 URL、PDF 物理页码及分页游标；读取后续正文不重新下载。只接受公开 HTTP(S) 的直接 PDF，下载不使用浏览器 Profile 或登录状态。付费墙、密码保护或不可提取的扫描内容会报告限制。

## Flash 提交与恢复（2026-11-07）

Desktop/Mobile 的输入提交在事件循环入口执行，避免在线程池中持久入队后创建异步执行失败。Flash 启动同时记录 Todo 与 Agent Run，恢复时可按原提交的 launch receipt 补齐关联，包括已经完成的旧提交；关联修复不重新执行工作流。

App-Dev 原生实测 `(12+3)*4 = 60`，提交成功后输入清空，任务完成且侧栏转圈停止，模型调用为 0。原 `3+3` 的已完成执行缺失回执已在重载时补齐，未重跑。详细回执见 `acceptance/flash-http-20261107/receipt.json`。

## Bot 列表顺序（2026-11-07）

拖拽排序保存在 Local 数据库中，按用户隔离，不依赖浏览器端口或 localStorage。新建 Bot 在当前排序末尾追加；排序提交中途出现的新 Bot 仍保留在末尾。列表 API 统一返回保存顺序，Desktop/Mobile 读取同一列表。排序只改变展示，不切换当前会话或启动任务。

## 受管任务继承 Bot Access（2026-11-10）

即时和定时 Todo 执行在启动时继承所属 Bot 的 App、Mini-App 和有向 Bot 权限。计划审阅可追加授权到 Bot。定时任务可用已有权限委派独立子任务并接收结果。旧计划需要重新审阅才能切换到继承模式。详见 [计划权限与审阅](bot-plan-access-preflight-v1.md)。

## Bot Access 条目（2026-11-07）

Bot 权限条目左侧显示跨两行头像，右侧首行显示单行省略的名称与删除按钮，次行显示“允许访问 / Allow access”开关。关闭开关保留条目；删除会撤销权限并从该列表移除，可从添加列表重新添加。移除记录只隐藏目录项，保留授权版本和历史回执，重新添加不会恢复旧执行权限。删除接口与开关共用 owner 的归属、版本和撤销逻辑，仅允许可信宿主操作。

固定 Dev/App-Dev 的 Bots 与好友并列；每个用户可创建具名、不可变职责的本地 Bot，头像显示名字缩写。重新选择同一个 Bot 恢复其 App Chat Session。关闭界面只释放显示控制器；Local 存活期间后台 Run 和已有任务继续。

注册 ai2apps.messager.bots 只接受当前用户拥有的 bot_id。名称、职责从服务端目录回读作为 scope 数据，不是授权。Messager owner 显式绑定情报中心已注册的 channels/search/news/read 四项已保存内容读取能力；具体查询、来源与结果解释沿用情报中心实现。未授予刷新、发布、微信工具、好友消息或桌面控制。模型可依据真实保存来源生成文本卡片草稿；没有来源时应明确告知缺口。不会主动或定时执行。

验收：创建两个同名或不同名的 Bot；提问、退出页面，返回原 Bot 可见任务结果，另一个 Bot 历史独立。切回好友仍使用原好友输入框；Bot 身份不充当 peerUserId。开发环境 SQLite 目录独立，切换用户不能读其他用户的 Bot。未在 Test 与生产注册此 owner。

## 下一阶段：在对话中配置 Bot（设计，尚未启用）

配置入口是用户与 Bot 的会话。区分三种持久对象：Bot 档案、定时委托、事件订阅。一位 Bot 可以同时负责多个不同时间或不同事件的委托。对话支持查看当前职责和规则，按规则修改、暂停、恢复或删除；不要只把承诺写入聊天历史。

1. **档案。** 名字、职责和偏好可修改，bot_id、所有者和原会话不变。当前 App Chat 用规范化 scope JSON 标识会话，而 Bot scope 包含名字与职责。先将旧 scope 迁为只含 bot_id 的稳定身份，保留原 session_id；读取最新档案作为 owner 上下文，已开始的一轮保留其档案版本。修改记录旧/新版本并检查 expected_revision；名字或职责变化不增加工具授权。
2. **定时。** “每天早上 6 点整理 AI 新闻”生成一条可查看的具体规则：哪个 Bot、哪个时区的 06:00、读取哪些来源、是否主动刷新、写到哪段对话。缺少时区时展示采用的用户时区。以 System Tasks 持久调度，按日历计算下次运行，确定休眠错过后只补最近一次还是跳过。每次以规则 ID、版本、计划发生时间去重；后台结果回到原 Bot 历史。Todo 的 reviewed agent flow 提供计划预览、确认、撤销与执行的先例，但其自身 app/owner/权限不是 Messager 授权。
3. **事件。** 先支持 AI2Apps 好友来信。messager.message.received 已和 Local 入站消息在同一事务落库；Cloud 离线消息导入 Local 时也发出该事件。事件是已入库观察，不是屏幕 Hook 或实时 Cloud 到达保证。关闭页面后的 Cloud 收件同步需另行验证。使用 EventStore 增量游标加提交唤醒；从订阅启用时开始，事件回放、崩溃恢复均按订阅 ID + 事件 ID 建立唯一工作项。按 owner、入站方向、发送者范围、来源和订阅状态过滤后，按引用读取正文；不让前台 SSE 承担后台执行。
4. **紧急来信委托。** 启用前让用户看到紧急判定标准、是否允许私信进入所选模型、可自动回复的范围和固定回复、Todo 目录、微信连接和“提醒我”的具体目标。来信仅是待判断的数据，不能改变委托。分类返回紧急/不紧急/不能判断及理由；不紧急不外发，无法判断按用户规则留待复核。仅对紧急消息执行已授权动作。每步分别记录状态、稳定请求键及业务回执；提醒失败不重建已成功的 Todo，不重复回复。发送结果未知先核对，不能静默切换微信账号或通道。对方为自动回复、重复入站或同一事件的回声时抑制循环。暂停/撤销后，未提交的动作在每一步前重新检查。
5. **阶段门槛。** 先验证改职责后同一会话可恢复，再验证定时、跨零点/休眠和重启；最后用合成入站事件验证两用户隔离、非紧急零副作用、重复事件、部分成功、撤销、通知结果未知。正式启用后台外发前，以明确测试目标单独实测回执。微信 CLI 的单次手工成功不是长期代发授权；微信官方通道的主动提醒另需能力验收。

事件声明、发布身份、跨库投递与恢复规则以[平台业务事件与订阅 Hook 设计 v1](platform-events-and-bot-hooks-v1.md)为准。

## 普通问答卡提交回执（2026-11-07）

普通 menu/text/form 问答继续提交到原 Run 的持久 Interaction，不改变权限和执行路由。点击提交立即禁用输入与按钮并显示“正在提交”；只有响应接口成功后才显示“已收到回复，任务将继续处理”，保留只读答复并隐藏提交按钮。这仅确认回复送达，不表示任务已完成。

本页面记住已经确认提交的 Interaction ID，忽略提交前发出的旧轮询快照，避免旧表单重新变成可提交状态。下一条不同的 Interaction 正常替换回执；切换 Bot 或卸载页面不把迟到响应写入新问题。请求失败不声称送达，保留答复并允许用户重试；答复未修改时重用 response_id，修改后才生成新的幂等键，不自动重放。

所有改动位于 Messager owner 前端，未改动 General Agent、业务声明、后端确认/取消/归属守卫或图片展示。定向前端夹具覆盖重复提交、未知送达、修改后重试、迟到响应与旧轮询竞态；原生 App-Dev 仅验证刷新与输入就绪，没有代替用户提交真实回答。证据位于 `docs/acceptance/bot-answer-receipt-20261107/`。

## 时间与排程（2026-11-09）

普通 Bot 消息与 Poke 由宿主采样 UTC，按客户端 IANA 时区计算当地日期和时间。缺少时区的旧客户端使用 UTC。快照与原请求一起持久化，重复请求沿用原快照。普通对话可直接使用它回答时间、日期和星期。任务启动时获得实际执行时钟，长任务可调用 `agent.current_time` 获得新的读数。

新 Bot 计划使用明确指定的时区或当前请求时区。已有计划在修改时默认沿用原时区。Todo 将 `delay_minutes` 和原请求的时间转换为一次性 UTC 执行时间，并使用已有时区与夏令时规则计算下一次执行。审阅卡按计划时区显示预计下次执行。已过期的一次性安排需要重新审阅。

对话使用已有的只读 Todo 运行投影。最近执行记录带有实际状态、起止时间和有界的已记录错误，可用于回答任务进度或失败原因。
