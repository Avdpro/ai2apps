# Bot 记忆与任务历史开发计划 v1

日期：2026-11-04。状态：M1/M2 核心及自动记忆维护/有界召回已实现，已通过门禁及针对性验证并加载 App-Dev。当前实现范围和保留项分别见 [M1/M2 核心](bot-memory-history-m12-implementation.md) 与 [自动记忆 v1](bot-memory-automatic-v1.md)；本文仍保留完整目标，不把未来规划视为已完成，也不自动开放新权限。

关联设计：[Messager UI 与 Bot Task](messager-ui-and-bot-task-v2.md)、[AaAT 声明与 Context 契约](aaat-declaration-context-v1.md)。

## 1. 目标与分层

近期消息和最近 20 个 Task-Session 是初始 Context 预算，不是历史可查范围。将能力分为：

| 层 | 内容 | 读取方式 |
|---|---|---|
| 近期工作上下文 | 最近聊天、正在执行/排队的任务、近期摘要、已选任务 | 每轮有界加载 |
| 长期记忆 | 用户事实、偏好、约定、有意义的资源关联 | 少量必要信息常驻，其余按需召回 |
| 任务与产物历史 | 原始要求、执行步骤、结果、输入/输出资源、版本关系 | 搜索摘要，按需读取详情 |

核心案例：用户提供本人照片；隔超过 20 条消息及超过 20 个任务后，提出“用之前戴帽子的熊猫和我合影”。Bot 应分别找回本人参考照片和指定熊猫版本，校验实际资源后执行；存在实质歧义时展示候选缩略图询问。

## 2. 结构化记录与资源保存

在既有 BotMemory owner 上演进，不另建一套绕过 UI/访问检查的记忆入口。旧便签保留、版本迁移明确，不从历史正文批量猜测用户事实。

建议持久结构：

- Memory：稳定 ID、actor/Bot、类型（事实/偏好/资源关联）、subject、predicate、value 或资源引用、适用范围、有效状态和当前版本。
- MemoryVersion：不可变的修改前后内容、适用时间、替代关系；区分“记录时间”与用户表达的生效时间。
- Evidence：来源 Session/消息/Task-Session/Run/step、原问题和回答关联、用户明确表达的用途、记录方式（手工/明确请求/问答关联/模型候选）。合并后保留多份证据，不丢来源。
- MemoryMutation：新增、补充来源、合并、替代、遗忘、撤销的持久回执及幂等键、版本前提、关联提示消息。
- ResourceReference：已有 owner 的稳定 Artifact/Asset 身份、媒体类型、所属资源、可用状态；不能将临时下载 URL 当资源身份。

索引键采用 actor + Bot + subject + predicate + scope；同一字段可声明单值或多值。自由文字不能直接作为可靠去重键。来源、关系和名称是数据，不构成系统指令、执行授权或任意回调。

照片复用现有素材存储与保留机制，建立可持久访问的引用。多个任务的引用尽量指向同一底层素材，不为每条记忆复制文件。文件指纹只用于识别同一文件；不能仅凭视觉相似就认定是同一个人。

## 3. 自动记录触发与成本控制

自动记录由明确的交互状态和既有对话决策触发，不为每条消息额外跑一次完整记忆分析：

| 触发 | 候选形成方式 | 默认处理 |
|---|---|---|
| 用户明确要求“记住/以后用/以后叫我” | 复用当前回合的结构化决策 | 保存候选并排入记忆 Task，提交成功后提示 |
| 用户回答 Bot 等待的问题 | 关联原问题的预期对象/资源角色和实际消息/附件 | 含义唯一时形成候选并排入记忆 Task；缺少长期用途依据时仅保留任务事实 |
| 普通对话出现可能长期有效的内容 | 当前已有模型调用顺带返回有界候选 | 低确定性保留为候选，必要时澄清，不直接覆盖事实 |
| 任务完成或产物生成 | owner 保存实际结果与谱系 | 更新历史索引，不将所有产物自动升格为长期记忆 |

本人照片案例：Bot 正在等待“你的本人照片用于合影”，用户针对该问题上传图片后，先验证附件归属和保存成功，形成“当前用户的合影形象参考”候选；由排队的记忆 Task 检查、合并和提交。这一步不必新增视觉调用。原合影任务可使用用户本次直接提供的照片，无须等待照片成为长期记忆。随手上传的人物照片不能自行认定为用户本人；不从照片推导无关身份属性。

问答关联须指向真实待回答项，不能仅凭时间接近，把另一个任务的附件当回答。候选只能引用当前 owner 已验证的消息、资源与对象。

允许宿主在用户消息/交互回答持久化、可信任务终态等现有节点调用记忆 owner；如使用 Event/Hook，保持相同来源绑定。以来源消息/交互 + 关系键幂等处理。记忆提示、合并回执和记忆内部事件不再触发同源提炼，防止自循环与递归创建任务。

成本策略：明确问答关系、相同资源和精确键匹配先走确定性处理；语义候选复用已有模型回合。合并模型只读取本次候选、相关字段的少量现有版本与必要证据，不重送全部聊天、所有记忆或图片。额外整理调用需有次数、Token 和队列上限；没有变化不整理。不得为“记住引用”再次完整分析图片。

单独统计新增模型调用数、输入/输出 Token、召回大小、记忆整理耗时、无变化率和用户撤销率。已有对话调用中新增的输入/输出也计入增量，不能只统计独立整理调用。预算不足或模型失败不阻塞普通聊天，不丢用户输入；候选保持待处理，未提交前不能提示“已记住”。

### 3.1 记忆处理作为独立 Bot Task

对话阶段只做有界候选输出、来源绑定和小规模持久入队，不等待记忆去重、语义分析、合并模型或写入结果。记忆加入/合并由独立的 Bot 维护 Task 执行；确定性操作也经过该 Task，但不因此强制调用模型。

复用现有 Todo 执行器、Bot 串行 lane、取消/恢复及 owner adapter，标记独立的 memory-maintenance 类型，不能伪装成用户普通创作 Task-Session。该 Task 只能访问对应候选、已授权来源和 BotMemory owner 的所需读写操作，不因来自某个 Bot 就继承所有 App 权限。

调度次序：

1. 当前已准入、正在执行的 Task 保持原样，记忆 Task 不抢占、不取消、不改参数或 Context；原任务正在等待输入/审批时也不能以记忆优先级绕过其占位规则。
2. 当前执行释放槽位后，已就绪的记忆 Task 可排到尚未开始的普通 Task 之前；同一 Task-Session 的待执行续接同样属于尚未开始的工作，不能中途修改正在执行的轮次。
3. 普通待执行任务之间保持既有顺序。记忆 Task 使用单独类别和可信优先级，用户/模型不能通过传任意 priority 参数扩大调度权限。
4. 同 Bot 的同源/相关候选可合并进尚未准入的一个批次；已开始的记忆 Task 固定输入，后到候选进入下一批。设置批次大小、执行时间和连续优先批次上限，并保留普通任务老化机制，避免持续新消息饿死普通队列。

前台聊天与 lane 独立，记忆 Task 的 queued/running 状态不禁用输入框，用户可以继续直接问答或创建其他 Task。共享模型/Runtime 请求沿现有资源预算调度，记忆整理不能抢占当前业务任务的模型执行；前台回复不等待整理结果。记忆 Task 失败、取消或预算不足应让出执行机会，不反复高优先级重试或卡住整条队列。

候选到 Task 通过持久引用/幂等入队衔接；重启恢复同一 Task 和变更回执，不重复保存来源、写入记忆或发送提示。开始执行和提交时校验当前 actor/Bot、来源/资源可用性、候选取消状态、遗忘水位和记忆版本；排队期间被清理的来源不能被后来的 Task 重新写回。

需要用户澄清的记忆冲突通过原对话流发问，并保存可恢复等待项；结束当前维护执行片段、释放槽位，不让尚未明确的一条称谓或照片阻塞后续普通工作。用户回答后准入同一记忆 Task 的后续执行，再复核版本；新聊天不能被误作该等待项的回答。

正在执行的普通任务保留其准入时的记忆快照。记忆提交不改写它的模型消息、缓存或已批准参数，也不为了刷新记忆重启任务。尚未准入的工作是否采纳新版本，必须遵循其 owner 的上下文/计划快照规则；特别是已审阅定时计划，不因记忆 Task 插队就更新原方案。新对话回合可以读取已成功提交的新记忆。

新增/合并的实际数据库写入仍在记忆 owner 内原子完成，Task 身份、候选集合、版本前提和变更回执一起绑定。用户直接编辑/撤销/清理通过相同版本与失效规则协调，不能被稍后执行的旧候选覆盖。撤销的失效标记和候选取消可立即提交；若需要复杂合并回滚，则由记忆 Task 处理，且不改写当前正在执行的业务任务。

## 4. 去重、合并与冲突

合并必须先识别对象、字段、用途范围和时间语义，不能采用全局“最后一条消息覆盖前一条”的规则。

| 情况 | 处理 |
|---|---|
| 同一内容/同一资源、同一用途再次提供 | 合并为同一条记忆，补充来源与最近确认时间，不重复占条目 |
| 同一字段的兼容补充 | 生成新版本，保留已有有效内容和新证据 |
| 用户明确要求替换单值字段 | 新版本成为当前值，旧版本标记被替代，保留可撤销关系 |
| 本次任务的临时要求 | 仅覆盖任务/会话范围，不修改长期默认值 |
| 不同用途或明确的多个备选 | 保留多个资源/取值，分别标用途和默认状态 |
| 冲突但无法判断是替换还是新增 | 对话中说明旧值、新值和不确定点，只询问必要选择 |

本人形象：两个 Task 提供同一文件时合并证据。提供不同的本人照片时，可作为同一用户的多个参考，不自动删除旧图或更换默认图；“以后用这张”才明确替换相应用途的默认引用。缺少选择依据时展示候选。

称谓：“以后叫我老王”建立默认称谓；后来“以后改叫我王老师”替代默认值；“这次扮演里叫我船长”只对该任务生效。仅出现另一个名字或被第三方这样称呼，不能推断用户要求修改默认称谓。

记忆含用户手工编辑时，模型候选不能静默覆盖。通过语义合并提出替换也必须符合用户明确意图；事实相似不等于字段相同。不同 Bot、用户、任务范围不能无授权合并。

候选审阅/提交绑定现有记忆版本，以比较并更新（CAS）保证并发安全。多个任务同时贡献相同资源时只产生一个当前条目和各自证据；版本冲突时重新读取并判定，不反复发布提示或覆盖后来的选择。

## 5. 对话流里的提示、查看与撤销

候选入队与记忆生效是两个状态。用户明确要求记住时，Bot 可以立即反馈“已收到，当前任务结束后整理记忆”，并提供待处理状态；不能在 queued/running 时宣称“已记住”。一般自动候选可在来源消息旁显示轻量“记忆待整理”状态，批量合并避免刷屏。等待期间可以查看/取消候选；取消阻止写入，不删除此前有效记忆，也不影响当前业务任务。

凡实际改变有效记忆、证据或默认引用，提交成功后在来源对话的对应位置产生轻量持久提示：

- “已记住：使用这张照片作为你的合影参考。”
- “已合并：沿用已有本人参考图，补充了这次任务的来源。”
- “已更新称谓：老王 → 王老师。”

提示带“查看”和“撤销”，与真实 MemoryMutation 回执绑定，不能由模型说一句“已记住”代替落盘。查看展示内容/图片预览、范围、来源、合并依据与前后版本；右侧 Memory 面板展示相同记录。默认不在信息流暴露原始 ID、JSON 或推理过程。

失败提示说明尚未写入及可处理原因；等待澄清说明哪个记忆字段拿不准。相关队列/阶段状态由实际 Task 回执投影到原提示，刷新后可恢复，不为状态反馈额外调用模型。

语义完全无变化且没有新增证据时不产生新变更或重复提示。同一回合多条相关变更可聚合成一张提示卡，卡内逐条查看/撤销；批量撤销必须明确展示包含哪些变更。无需再次调用模型生成状态文案。

撤销作用于所选变更，不是删除整个记忆集合：

- 新增：使本次新增记录失效；若后续已有独立证据/编辑，先检查依赖，不直接抹掉后来的信息。
- 合并：移除本次贡献及其引入的字段，保留此前的内容和其他来源。
- 替换：在没有后续冲突修改的前提下，恢复此前当前值；保留版本审计。
- 出现后续版本/依赖：显示当前状态和冲突，让用户选择目标，拒绝陈旧按钮的盲目回滚。

撤销也是有版本和幂等键的新变更，刷新、重启、重复点击不会重复生效。原提示标为“已撤销”，不删除原始事实记录。取消记忆不撤销已完成的图片生成/消息等业务效果，也不改变 App Access；已执行任务保留其实际输入审计，后续 Context 不再使用失效记忆。未准入任务使用的记忆被遗忘/资源不可用时，需重新解析或等待用户，而不能静默继续引用。

## 6. Task 与产物历史查询

建立 Task-Session、step 和产物的元数据/全文索引：标题、用户目标、实际结果摘要、时间/状态、资源描述，以及输入→输出、修改动作、版本、所属 actor/Bot 和可见范围。任务摘要不能冒充成功记录；保留失败/部分完成/取消的真实状态。

Messager owner 通过 AaAT 提供搜索、任务/步骤详情、产物详情与版本谱系读取。结果有分页、数量和 Context 上限，附匹配依据和实际引用。先用 SQLite 元数据和全文索引，再以质量证据决定是否补语义检索；不得靠增加常驻 Task 数无限扩大 Context。

历史引用触发有界检索阶段：“之前那个戴帽子的熊猫”先找对应产物；唯一且资源有效时自动采用，多个近似版本时展示缩略图选择。结果查到后再加载必要原文、输入资源和谱系，不将全部历史全文送入模型。General 保持业务无关，对象含义、检索范围与证据由 owner 声明。

## 7. Context、权限与遗忘

每轮流程：近期 Context + 必要长期记忆 → 判断缺少的事实/历史引用 → 按需检索 → 消歧 → 直接回答或创建/续接任务。记忆候选与检索都不是新的授权依据。

任务准入记录所采用的记忆版本和资源版本，不在执行中静默替换。定时任务默认沿用已审阅的快照，新默认照片/称谓不自动重写旧计划；需要更新时走原计划版本流程。既有 Actor/Bot/Session、Provider、App/Mini-App 访问 及敏感/付费确认保持有效。

清除对话默认不召回其已归档内容；显式保留的长期记忆继续有效并保留来源标识。清除/撤销记忆建立遗忘状态和来源处理水位，避免旧消息被后台重新提炼后复活。用户明确重新提供事实或要求重新记住，可以产生新的有效版本。撤销一次错误合并不能被当作删除其他独立来源。

记忆遗忘不删除任务审计或共享素材；默认任务历史检索不得把已遗忘的个人关联自动恢复为身份事实。素材删除/权限撤回要使引用不可用，并移除相关主动 Context/检索预览；索引命中不等于实际读取授权。恢复对话不恢复记忆、资源访问权或调度。清理选项沿用现有确认框。

## 8. 实施阶段与验收

| 阶段 | 开发项 | 验收重点 |
|---|---|---|
| M1 历史与资源 | 稳定资源引用、Task/步骤/产物索引、谱系、搜索/详情 AaAT | 超过 20 个 Task 仍能找回戴帽子熊猫，歧义可选，失效资源明确报告 |
| M2 结构化记忆 | 记忆/证据/版本/变更回执、记忆 Task owner adapter 与优先排队、确定性去重与替代、信息流提示/查看/撤销 | 同图跨任务合并、称谓更新/临时覆盖；聊天不等待，当前 Task 不被抢占；重启后队列/回执一致 |
| M3 自动记录与召回 | 明确请求/问答关联形成候选并入队、已有模型候选、语义合并、按需召回、成本计量 | 照片问答无需额外视觉调用；隔长对话仍可合影；不重复保存、无自循环、普通队列不饿死 |
| M4 管理与遗忘 | 搜索/查看来源、资源替换、遗忘阻止复活、清理索引和依赖管理 | 撤销不误删后来信息，清理后不复活，不恢复权限/任务 |

M2 的来源/版本、提示和撤销必须先于 M3 自动写入开放；M4 最小的遗忘与防复活约束也必须随首次自动写入一起具备，其余管理体验后续完善。

自动维护与有界召回已接入；不批量改写既有便签或回溯提炼旧消息。确定性维护不增加模型调用，按需召回最多增加一次对话判断，新增 Context 不等于零 Token 开销。涉及 AaAT 的集成遵守现有门禁，测试记录区分夹具与真实模型执行。
