# AaAT 频道与跨 App 调用统一方案 v1

日期：2026-11-01  
状态：设计提案／待实现。本文记录讨论确定的方向，不表示所列字段、SDK、错误码和流程已经实现。示意名称须在实现时与现有契约对齐并做版本评审。

MVP 进度：已实现静态内置频道和系统管理端只读调用子集，具体范围与未实现项见 [Channels MVP v1](aaat-channels-mvp-v1.md)。后续已实现独立 [只读系统参数纠错 v2](aaat-read-parameter-repair-v2.md)；持久调用恢复、写操作和无 Run 确认等其余流程仍为待实现设计。

## 1. 目标与决定

以 AaAT 作为 App、Mini-App、App Agent 和 Agent-Chat 唯一的能力接入体系。所谓“系统信息”只提供薄的频道发现、定位与导航，不建立第二套执行器、授权系统、业务 API 或内容存储。

App 开发者维护一套业务服务和一份能力注册：声明自己的频道，绑定标准操作角色或自定义能力，即可供自身 UI、跨 App 调用和 Agent 使用。

统一实现参数校验反馈、自动修正、有界重试、持久调用恢复和系统级用户确认。默认尽量自主完成；目标能力要求真实用户确认时，调用 App、AI 和后台任务均不能代替用户确认。

本方案只扩展 Local 与已验证 Package 的接入契约。不直接修改 Cloud；若后续需要发布目录字段支持，另提交 Cloud 变更需求，由 Cloud 项目实现和部署。

### 1.1 现有 Agent-Chat 不受影响是硬性前提

系统信息／频道机制必须以增量入口和版本化适配接入，不得改变当前 Agent-Chat 的链路流程、默认行为及历史恢复语义。现有能力发现与声明复核、模型/Tool 循环、参数表单、确认认领、调用键、预算、取消、恢复和结果关联继续由原链路负责；不能因为频道建设而要求现有 Chat 改走新协调器或新增模型回合。

新机制关闭、不可用或初始化失败时，当前 Agent-Chat 仍须按原路径工作。新入口使用的配置、纠错预算、状态和失败不得污染现有 Run，也不得使旧 Provider 因缺少频道 facet 而不可调用。复用业务 handler 和可信校验代码不等于替换现有执行链路。

本提案不包含现有 Agent-Chat 的执行链迁移。未来若要让其采用新协调机制，必须另行提出明确范围、兼容性与回退方案，并经评审和授权后实施；不得将迁移隐含在本方案的共享代码重构中。共享基础设施确需扩展时必须保持旧接口和行为，并提供新旧入口并行回归证据。

## 2. 当前基础与缺口

当前已有：

- `services/capability_routing.py` 的 `CapabilityProvider`／`CapabilityRouter`：归属、版本、声明、发现、prepare、调用策略和结果策略。
- `intelligence/aaat.py` 的 channels、search、read、news 等能力，复用情报中心自身数据服务。
- `services/builtin_apps.py` 注册的 Gallery search/get；Knowledge 接入直接复用现有 handler、权限、检索和引用。
- 持久参数表单、Interaction、App continuation，以及已有任务观察与恢复机制。
- Package 的受信任导出、隔离 Service 桥接、生命周期撤销与版本守卫。

缺口：统一频道描述；不依赖 Chat 的调用入口和交互展示；机器可理解的参数错误；共享纠错与重试协调；不同调用界面复用真实用户确认。

现有 `discovery_context` 用于有界动态发现预览，不能变成全量内容数据库或授权来源。完整目录和内容继续通过所属能力按需查询。

## 3. 架构与所有权

```text
Chat / App / Mini-App / 后台任务
                │ 同一调用 SDK、可信身份上下文
                ▼
      AaAT 发现、声明复核、调用协调
         │                    │
    薄频道目录          持久 Interaction
         │              Chat / Shell / Mobile 展示
         ▼
   CapabilityRouter / 现有 Tool Gateway
                ▼
        所属 App 的业务服务与存储
```

- 频道目录：索引已验证的信息源声明，执行调用方可见性过滤，定位频道及其能力绑定。动态频道由 owner 查询产生。
- AaAT：统一调用、授权上下文传递、声明复核、预算、纠错协调、交互、取消、恢复和审计。
- 所属 App：业务语义、层级关系、统计口径、资源定位、参数校验、访问控制、确认要求和真实执行。
- 展示宿主：展示同一持久交互，不自行批准，不拥有业务执行权。

共享执行代码不得根据 App ID、Tool 名、站点或业务字段分支。注册组合层可以绑定 owner；运行时通过可信契约决定行为。

## 4. 一次注册：频道与能力绑定

### 4.1 频道声明

在现有受信任能力注册／导出契约增加可选频道 facet。它与 AaAT 能力共用版本、安装与撤销生命周期，不建立独立注册来源。

建议包含：

| 信息 | 含义 |
|---|---|
| namespace、local_id | owner 范围内稳定标识 |
| name、description、aliases | 多语言名称、描述及检索别名 |
| parent_ref | 可选父频道引用 |
| content_types | 文章、图片、音频、视频、文档或自定义类型 |
| operations | 操作角色到具体已注册能力的绑定 |
| discovery binding | 动态子频道的发现／定位能力 |
| interface_version | 频道接口版本，与 Provider 版本共同守卫 |

声明只描述能力，不授予权限。动态标题、正文和查询结果始终是业务数据，不能成为可信指令。

### 4.2 操作角色

| 角色 | 用途 |
|---|---|
| resolve | 名称、自然语言或已有引用定位实际对象 |
| list | 分页列出子频道或内容 |
| search | 在指定范围检索 |
| read | 读取指定内容 |
| add | 创建内容或对象 |

不要求每个频道支持全部角色。删除、更新、刷新、生成、移动等继续注册为具体 AaAT 能力，也可在明确版本的扩展角色中绑定。

统一的是角色、引用、分页和结果外壳，不是所有业务参数。情报中心添加新闻、Todo 添加项目、Gallery 添加素材各自保留输入 Schema 和业务规则。自定义能力继续通过原 AaAT 发现机制公开。

### 4.3 资源引用与结果

引用应携带 owner／Provider、频道或资源 ID、资源类型及必要的接口版本；显示名称和路径不充当身份。接口升级不要求重写已有业务 ID。

列表和搜索结果提供稳定引用、标题、类型、摘要、可选缩略图、来源、时间以及 cursor；返回实际 scope、coverage、truncated。无法取得总数时不得用本页数量冒充总量。正文和大媒体按需读取，媒体使用受控引用。

引用不是 bearer 凭据，读取时重新检查权限。跨来源排序可由目录聚合，统计语义、递归范围和事实引用仍由 owner 提供。

### 4.4 典型映射

- 情报中心 → AI／腕表等频道 → 模型发布等栏目。
- Knowledge → 知识库／知识桶。
- Gallery → 现有集合与目录。
- Studio → 共享 Output 的查询视图，例如最近生成的图片；不得新增 Mini-App 私有输出历史。
- 浏览器 → 已授权的历史／收藏视图。
- Todo → 项目或目录；是否作为频道公开以及可添加哪些对象，由 Todo 声明。

这些是注册适配示例，不进入通用 Agent 的业务判断。

## 5. 薄目录与自然语言发现

1. 精确引用直接定位 owner，并复核当前可用性和权限。
2. 自然语言先通过可见的名称、描述、别名和类型找到候选。
3. 调用候选 owner 的 resolve／search，获得真实频道或资源。
4. 选定后按现有 AaAT 流程加载完整声明和 Provider 版本，再调用绑定能力。
5. 实质歧义无法消除时才请求用户选择；禁止交互时返回结构化歧义结果。

例如“推广视频里的图片”：目录发现支持图片与集合检索的候选，Gallery 自己定位该集合并定义搜索范围。系统不能根据词语擅自拼接目录 ID。

第一阶段仅使用声明与 owner 检索能力；语义索引可后续增加，但只能作为权限过滤后的发现缓存，不能形成第二份权威内容库。缓存需要随访问权、Provider 和安装状态变化失效。

## 6. 跨 App 调用上下文与 SDK

调用 App 提交意图、目标能力／频道、参数、必要引用、稳定 request_id 及交互偏好；身份由宿主验证和注入，不允许通过参数冒充。

宿主上下文至少绑定：actor、Installation、调用方 App/Mini-App、目标 Provider/版本、Session/Run 或持久调用记录、委托权限范围、预算和调用链。

App-to-App 不要求创建 Chat 或模型回合。简单调用直接返回；需要持久等待、恢复或写操作去重时，沿用现有 invocation／Interaction／任务设施。实现前盘点现有仓储，避免增加竞争执行记录。

SDK 提供统一的 invoke、get/follow、cancel、resume 等使用方式；具体命名待接口评审。前端刷新或重连只读取／恢复原调用，不重新提交。

调用方权限与用户权限共同约束实际访问；用户能够读取不代表任意 App 自动可读。后台委托不得扩大父调用权限或预算。嵌套调用传递来源链、限制深度并防止循环；子调用不能自行取得额外授权。

### 6.1 权限来源与授予

调用方通过可信注册请求目标能力、资源范围和效果类型；Package 请求来自已验证的签名声明。声明只提出请求，不授予权限。目标 owner 定义可开放范围和业务访问规则；现有宿主授权设施记录用户或既有管理策略实际授予的委托，不建立频道专用授权系统。

有效权限取用户当前资源权限、调用 App 已获委托、目标 owner 规则、父级委托与平台限制的交集。发现、正文读取、写入和结果交付分别校验；允许发现不代表可读取，用户可读取不代表任意 App 自动可读取。缺少委托时使用宿主授权交互；禁止交互时返回结构化权限需求，不扩大权限。

宿主从认证连接注入 actor、Installation、调用 App/Mini-App、已验证 Package 版本和当前 mount/session，禁止参数覆盖。委托绑定这些主体、目标能力、资源范围、效果类型、期限和授权版本。后台仅接受宿主签发的持久委托，不自动延长页面会话权限。刷新后的新 mount 必须重新认证后才能观察或续接原调用。

撤权、到期、退出账号、禁用或卸载使相关发现缓存及旧续接授权失效，并阻止新的执行和结果读取。已开始的效果是否能停止由 owner 协议决定；撤权不表示回滚。可信宿主可保留内部对账记录，但不得绕过撤权向调用方交付结果。

### 6.2 结果与调用链权限

get/follow、错误候选、进度、结果和媒体引用都校验当前观察者、原调用归属、当前委托与源资源权限；invocation_ref 不是访问凭据。跨 App/Session 交付资源须由 owner/宿主建立目标范围内的受控引用，不转发原始路径、凭据或永久访问权。

嵌套调用保留原始发起方及每一跳身份，不能借目标 App 的更宽权限替调用方读取数据。子调用预算从父级扣除，资源及效果范围不得扩大。调用委托、业务许可和真实用户效果确认分别校验，不能互相替代。

## 7. 系统级参数修正

### 7.1 责任与错误契约

调用 App 提供初始参数和原始意图；目标 App 是最终校验者。参数纠错是系统调用协调器的职责，可以调用 AI。系统统一负责错误识别、候选生成、复核、有界重试与停止；新跨 App SDK、新协议 Agent 适配入口和后台入口复用同一协调器，不各自叠加纠错模型或重试循环。当前 Agent-Chat 保留原有模型纠错路径，不自动接入新协调器。业务校验仍由 owner 提供。

建议错误外壳包含以下信息；名称为提案：

- code：validation_error、ambiguous、not_found、permission_denied、confirmation_required、version_conflict、transient_failure、execution_unknown 等。
- field_errors：字段路径、约束、错误原因及可安全公开的候选引用。
- execution_state：not_started、committed、unknown；只能由可信执行层／owner 协议确定。
- retry：是否可修正、是否可重试、建议等待及所需重新读取的版本。
- invocation_ref：原调用引用；错误展示信息须去除凭据和无关隐私。

错误文本、业务返回的候选和建议都是数据，不能自行授予权限或指定任意可执行代码。

### 7.2 修正流程

1. 校验可信输入 Schema 与 prepare 规则。
2. 失败后先使用 Schema、owner 声明的规范化规则或参数默认值修正；不能自行把空值与缺省值视为等价。
3. 确定性修正不足、需要理解上下文时，系统可按有效策略和预算调用 AI。仅提供当前可信契约、原始意图、必要授权上下文和结构化错误。AI 只提出参数候选，不能批准执行、编造资源 ID、补造许可或决定效果状态。没有可用模型时返回可解释的未修正错误，不静默扩大预算或数据范围。
4. 对候选重新检查 Schema、权限、owner 校验和原意图范围。
5. 在同一逻辑调用下创建有界的修正尝试；记录每次参数变化、原因和结果。
6. 相同参数与错误重复出现、预算用尽或无法可靠修正时停止，返回调用 App。

允许修正格式、受声明约束的类型等；不得擅自更换待删除对象、扩大查询／操作范围或改成另一项业务。候选有实质歧义时不猜测写操作目标。

当前规范“精确参数契约与纠错”禁止“调用另一层 AI 做意义映射”。本提案决定通过新版本调用协议引入系统可调用 AI 的纠错机制：由统一协调器生成候选并交 owner 校验，不增加业务专用映射器。阶段 A 必须同步评审规范修订与迁移；本提案不直接改变现有行为，旧入口继续遵守原契约；当前 Agent-Chat 的迁移不在本提案范围。

### 7.2.1 系统纠错与现有 Agent-Chat 的隔离

系统纠错面向显式协商的新调用协议。现有 Agent-Chat 继续把可信提交前错误交回当前任务模型，并使用原调用/结果关联及预算规则；不得在 Router 内隐式插入第二个 AI、吞掉错误回执或代替原模型重发。新协议由宿主认证的入口确定，不能由工具参数、返回内容或能力名触发。

除“无内层 AI 映射”外，旧契约的“宿主不合并冲突字段、不替模型重放”同样需要明确版本边界。规范修订必须保留旧入口原义，只为新协议定义系统纠错；不能以全局删除旧限制的方式开放。新协调器的纠错调用计入原逻辑调用预算，返回候选和审计记录，不启动新的 General Agent 执行循环。

纠错许可只能来自可信执行层判定的提交前阶段及明确白名单错误码。owner 的普通错误文本、handler 内 ValidationError、超时和断线不能证明未执行；不能把普通 validation_error 自动映射为 not_started。保留当前 parameter_contract_required/mismatch 的契约指纹、校验路径和完整可信契约，不把错误外壳转换造成的信息丢失当作可重试依据。

保留原始参数及已知值，不静默删除未知字段、选择冲突字段胜者或将空值等同缺省。规范化与候选改动使用独立记录，逐项复核；错误提示不回显参数值。确需 AI 使用的必要参数通过授权且有界的独立数据输入提供，不拼进错误提示或普通日志。确认之后不得直接改参执行；任何修正先使旧确认失效，再走 owner 校验与所需确认。

### 7.3 重试与效果状态

| 状态 | 系统动作 |
|---|---|
| 确定未执行的参数错误 | 可以修正后重试 |
| 已提交成功 | 读取原结果，不重复执行 |
| 暂时性错误且确定无效果 | 按策略退避，有界重试 |
| 断线／超时且执行状态未知 | 先对账原调用；无法确定则返回 unknown |
| 权限拒绝／用户取消 | 停止，不更换工具规避 |

逻辑 request_id 保持稳定。改变参数的修正尝试使用独立 attempt_id，并绑定父调用和参数摘要；不能以同一幂等键改参绕过现有拒绝。真正开始执行的 attempt 绑定稳定执行键。未知执行状态未对账前禁止创建新的效果尝试。

不能声称跨所有 Service 的 exactly-once；需要 owner 的幂等／状态查询支持。缺少这类能力的效果操作在不确定状态下必须停止。

## 8. 系统确认与交互

参数完整不等于已确认。参数收集、目标选择、权限授权和效果确认应有明确类型；一个普通参数表单不能自动替代删除确认。

必须确认由目标 owner 的可信策略规定，系统强制执行。调用方的“已确认”布尔值、AI 文本和工具结果不能作为用户确认凭证。保留现有 invocation_policy 与有效持久表单凭证的组合规则；新增明确确认类型时做版本迁移，不放宽旧守卫。

系统确认至少展示：调用来源、目标 App、具体对象、操作内容、影响范围及必要风险说明。目标 App 提供业务摘要，宿主标明可信调用来源并使用安全展示。

确认凭证绑定 actor、调用记录、Provider/接口版本、规范化参数摘要、对象版本、确认类型、有效期和取消状态；以原子方式认领。对象或关键参数变化后，旧确认失效，重新校验并确认。用户取消后不能自动重提或换能力执行。

同一 Interaction 按入口展示：

- Chat：卡片。
- 前台 App/Mini-App：宿主级弹层／侧栏，必要时打开目标工作区。
- 后台：持久等待，在允许通知时通过系统通知定位同一交互。

Shell、Mobile 和 Package frame 均通过受控宿主通道展示；Package 不得伪造系统确认层。关闭界面不等于取消，重启后恢复原交互。

### 8.1 无 Run 调用的确认归属与认领

“不创建 Chat 或模型回合”不表示无持久执行归属。新入口需要等待用户或产生效果时，必须先建立宿主拥有的持久 invocation；纯只读直接调用可以不创建 Run。不得伪造 Chat、空模型 Run 或借用其他 Run 的表单凭证来满足旧守卫。

阶段 A 必须明确现有 Interaction 仓储是否能以版本化方式支持非 Run 拥有者。若当前仅支持 Run 归属，须先设计通用拥有者适配：区分原 Run 与新 invocation，保持旧记录、外键、接口及认领逻辑有效；复用同一持久交互设施，不建立另一个审批数据库。适配未通过验收前，新无 Run 入口遇到必须确认时只返回 confirmation_required／不支持的结构化结果，不执行、不借用旧凭证。

| 拥有者 | 确认和执行关联 |
|---|---|
| 现有 Agent-Chat Run | 继续绑定原 Run、原调度调用键、精确参数和 Provider/表单版本；不更换键、不改变一次认领及原 Tool 结果关联 |
| 新持久 invocation | 绑定认证发起方、Installation、调用协议版本、invocation、attempt、原执行键、精确参数摘要及 Provider/表单版本；不依赖页面生命周期 |

两类凭证不能互换。共享展示可以定位同一条交互，但不能将 Run 确认复制成 invocation 确认，也不能通过“恢复”转移拥有者。参数摘要来自可信 owner prepare 后的规范化参数；提交时仍按既有精确参数/草稿 revision 规则校验，不放宽为语义相似。

认领必须原子绑定该拥有者唯一的执行尝试，遵守 owner invocation_policy 与有效 configure-only 表单的现有组合规则；不能因新增确认类型而跳过 policy 或重复批准。跨仓储无法同事务提交时，先持久化稳定关联并通过幂等认领恢复，不能以新键绕过已消费记录。多端提交、刷新、重启只返回原认领与结果；取消、过期、改参或版本变化阻止旧凭证复用。

## 9. 调用策略与预算提案

字段名及具体数值为新 SDK 的建议默认值，实施时需容量验证；不直接覆盖旧 AaAT 调用行为。

| 参数 | 新跨 App SDK 建议默认值 | 含义 |
|---|---|---|
| interaction_mode | allow | allow 或 forbid；允许交互不代表预先批准 |
| parameter_repair | system | off／deterministic／system；system 先确定性修正，必要时按有效策略调用 AI |
| max_repair_attempts | 2 | 参数修正次数上限 |
| max_transient_retries | 2 | 独立的暂时性重试上限 |
| total_timeout_ms | 继承父调用；无父级时采用平台配置 | 不新增隐式无限等待 |
| repair_model_budget | 继承父预算且受平台上限限制 | AI 成本计入原任务 |
| confirmation_wait | 沿用现有持久交互期限 | 等待期限与执行超时分别记录 |

system 是新版本入口的系统行为，不要求每个 App 单独实现或逐次启用 AI。平台模型与数据使用配置、父级限制、owner 策略及剩余预算共同限制 AI 使用；调用方可收紧为 deterministic 或 off。AI 不可用不妨碍参数已有效的直接调用。

旧调用未提供新字段时保持现有语义；新入口统一使用平台默认配置，owner 可收紧策略，调用方不能放宽 owner 强制要求或父级限制。

`interaction_mode=forbid` 时不弹窗、不发起用户协助；遇到必须确认返回 confirmation_required，不执行效果。系统不自动创建无人处理的无限等待任务。调用方以后请求交互式续接时，重新校验权限、版本及原状态。

禁止交互不会把错误转成成功。错误先交回调用 App，只有工作流确实需要且允许时才请求用户介入。

## 10. 持久性、任务与安全

- 调用状态建议表达 preparing、repairing、awaiting_user、executing、reconciling、completed、failed、cancelled；映射到现有状态机制，不建立第二套任务调度。
- 观察已有 System Task／Browser Task／Studio Job 使用现有 follow 与标准进度投影；频道读取和 AaAT 包装不能再占有一套竞争队列。
- 参数修正和等待用户不能重置总预算。恢复只继续未完成步骤，已保存结果直接复用。
- 权限在发现、准备、执行和读取结果时校验；撤销、禁用、卸载和版本变化使缓存及旧续接失效。
- 频道名、文章正文、错误提示和模型输出不能升级为系统指令。AI 修正仅接触授权、必要且有界的上下文。
- 审计保留调用链、声明版本、参数摘要、修正原因、确认引用、效果状态和恢复行为；日志不记录凭据或无关正文。

### 10.1 调用记录与键的归属

沿用现有持久仓储，阶段 A 明确实际字段与事务映射，不新增竞争队列。逻辑调用记录是协调状态的唯一权威；Interaction 只拥有交互状态，owner 任务只拥有实际执行与效果收据，协调器引用和投影它们，不接管其队列。

| 标识 | 作用域与规则 |
|---|---|
| request_id | actor、Installation、已认证调用 App/Mini-App 范围内唯一；首次提交原子绑定初始请求摘要、目标与版本 |
| invocation_ref | 宿主生成的原调用引用；重复提交返回该记录，读取仍需鉴权 |
| attempt_id | 逻辑调用内的独立修正尝试，保留前驱、参数摘要、契约版本及原因 |
| execution_key | 真正执行前持久化并绑定具体 attempt 与参数摘要；传输重试与对账复用，不能改参 |
| interaction_ref / task_ref | 引用原持久交互或 owner 任务；刷新、重连和恢复不另建执行记录 |

同 request_id 同初始请求返回原记录；不同参数、目标或协议版本返回冲突，不能覆盖原记录。系统纠错通过受控 attempt 追加参数候选，不伪装成调用方重新提交。调用方改变原始意图必须创建新逻辑调用；原调用效果未知时，新键也不能绕过对账。去重记录的保留期及过期行为须公开；记录过期不视作安全重放许可，无法确认效果时返回 unknown。

### 10.2 状态转换与恢复

协调状态与 execution_state 分开保存；failed/cancelled 不自动表示无效果。下表是语义约束，具体名称映射现有状态机制。

| 状态 | 允许的后续与恢复规则 |
|---|---|
| preparing | 鉴权、版本及 owner 校验后进入 repairing、awaiting_user 或 executing；拒绝则 failed |
| repairing | 追加有界候选后回 preparing；预算耗尽或无法修正则 failed；不得执行效果 |
| awaiting_user | 原 Interaction 有效提交后回 preparing，重验全部守卫；过期或取消停止，不自动重新弹出 |
| executing | 先保存执行键再派发；可信成功收据进入 completed，确定无效果的失败按策略处理，不确定则 reconciling |
| reconciling | 仅查询原执行键/任务；确定成功则 completed，确定无效果才允许受控重试；无法确定则停止并返回 execution_unknown |
| completed / failed / cancelled | 返回保存的结果或终止原因，不因重连重放；结果读取重新鉴权 |

执行未知时可将协调记录以 failed + execution_state=unknown 结束，保留原键及后续对账入口；用户显式请求的续接只允许先对账，不把终止状态重置为待执行。对账发现迟到提交时追加收据及效果状态，不抹掉取消或失败历史，也不自动触发下一项业务。

多端恢复使用仓储原子版本检查及单一有效执行认领。租约过期不证明无效果，不能据此重新派发；owner 需以稳定执行键幂等并拒绝过期认领，或只能进入对账。取消先持久化并禁止后续效果尝试；与提交竞争时以 owner 实际收据报告结果。已提交不能被标作已回滚；取消请求已接受但效果未知时继续标 unknown。跨 Service 无法事务提交时明确保留该不确定窗口。

### 10.3 版本与兼容边界

分别管理调用协议、频道 facet/引用接口、Provider 声明/参数契约、Package 签名导出版本；它们不能互相替代。每次调用保存协商版本、精确 Provider 版本和契约指纹，确认与执行尝试绑定这些版本。未协商支持的新字段不得静默忽略，能力目录只供发现，不注册 handler。

现有 Agent-Chat 不迁移，新机制失败也不影响其运行。旧入口缺省参数保持旧行为；新 SDK 经显式协议协商使用系统纠错和新错误外壳，不能仅因多传字段升级旧执行器。频道扩展缺失时旧能力仍可按原接口调用，但不能伪造频道支持。不兼容引用返回明确版本错误，不以显示名猜测替代对象。

Provider 或 Package 升级、撤销后旧确认与待执行续接失效。重读新声明、重验参数和权限并按需重新确认后，才可追加新版本尝试；目标与原意图不能改变。已完成结果可在当前权限下读取；已派发或效果未知的旧尝试只通过原执行键对账，不能拿新版本重放。无法对账须返回 unknown。

## 11. 实现拆分

### 阶段 A：契约与通用夹具

盘点 Provider、参数表单、持久 Interaction、Gateway、App Chat、Package 导出的现有机制，确定可直接复用的位置。设计严格版本化 Schema：频道 facet、引用、错误外壳、操作绑定和 SDK 调用策略。确定权限委托来源、存储事务、状态映射、去重保留期、版本协商及旧入口迁移矩阵；同步评审系统 AI 纠错对当前规范的修订。新增明确出口：完成新旧入口权限/状态/版本映射、非 Run 确认拥有者设计、系统 AI 纠错边界及 Agent-Chat 不受影响方案的评审，才能进入 B/C。以任意 alpha/beta Provider 验证，禁止依赖业务名称。

### 阶段 B：薄频道目录与只读调用

本阶段仅开放内置 Provider 的新频道接口，不开放 Package 新导出协议。扩展 `services/capability_routing.py` 及内置注册适配，生成受权限过滤的频道发现投影。先迁移情报中心、Gallery、Knowledge 的 list/search/read，旧能力继续可用并共用 handler。自然语言定位按需调用 owner，不加载全量内容。

### 阶段 C：统一调用协调与参数恢复

在共享调用层实现结构化校验错误、确定性修正、系统按需 AI 修正、预算和重试。新 App SDK 与新协议 Agent 适配使用同一个协调器，避免双重纠错循环；不改接当前 Agent-Chat。为效果能力先补足 owner 幂等和状态对账契约，再允许恢复执行。

### 阶段 D：宿主级确认与写操作

复用持久 Interaction，实现 Chat／Shell／Mobile 展示适配；Package 先做受控桥接夹具验证，正式开放须通过阶段 E。先用任意 Provider 验证，再接入添加新闻／创建项目等实际 owner 能力；删除确认验证真实用户凭证绑定和失效规则。

### 阶段 E：Package 与更多频道

正式开放 Package 新频道与跨 App 协议前，必须完成签名导出 Schema、SDK/宿主版本协商、安装对账、权限隔离、确认、撤销和升级测试；旧 Package 仅保留已验证的旧能力，不能推断支持新协议。若需提前接入，必须将上述门禁整体前移，不能只提前导出字段。接入共享 Studio Output、浏览器历史／收藏。目录或签名发布协议若涉及 Cloud，独立编写需求并交由 Cloud 项目处理。

上述文件为预计接入位置，不代表允许把所有实现堆入 CapabilityRouter。执行、交互和业务适配应保留现有分层。实现时同步更新规范契约和开发指南。

## 12. 验收标准

以下 Agent-Chat 保护项是所有阶段的前置门禁：新机制开启、关闭、初始化失败及运行故障时，既有 Chat 的发现/describe、参数纠错、configure-only 确认与 policy 组合、取消、重启恢复、未知效果处理及最终结果关联均保持原行为。旧 Provider 无频道 facet 仍正常调用；不新增模型回合、不重复表单、不替换原调度键、不重复执行。用同一组既有用例及新旧协议并行场景验证；不能仅以新入口夹具成功作为兼容证据。

非 Run 确认须覆盖拥有者隔离、跨 Run/invocation 凭证拒绝、并发认领与重启恢复；系统纠错须覆盖旧 Chat 零新增内层 AI、新入口有界 AI 修正、handler 校验错误不重试、改参后旧确认失效、预算及参数隐私。相关迁移适配未通过前不得开放需确认的无 Run 效果调用。

1. 一份注册使同一业务 handler 同时服务 App 和 Agent；无第二套业务实现或内容库。
2. 层级频道、虚拟集合、分页、跨源引用和自然语言歧义有可验证结果。
3. 不同用户、调用 App、Installation、会话与委托范围互相隔离；目录不泄露不可发现资源。
4. 参数错误可修正且有界；歧义写对象不被替换；相同错误不死循环；AI 修正不扩权。
5. 对具备 owner 幂等与对账支持的能力，验证超时、断线、重启、重复提交和并发认领不产生重复效果；缺少支持或无法确定状态时停止，保留原执行键与对账入口，不承诺跨 Service exactly-once。
6. 前台、Chat、后台和 Mobile 使用同一确认记录；取消、过期、改参、对象变化及 Provider 升级均正确阻止旧凭证使用。
7. forbid 模式零用户协助；必需确认时零效果；允许续接时重新校验。
8. Package 升级／禁用／卸载即时撤销频道与能力，旧回调不能继续执行。
9. Studio 使用共享 Output，现有业务统计与引用语义保留。
10. 验证同键异参冲突、租约失效、取消/提交竞争、迟到收据、撤权后的结果隔离、新旧协议协商及旧版本未知效果不重放。通用机制使用任意／不同 Provider 覆盖；业务 owner 测试另行执行。UI 验收明确区分夹具与真实执行。

涉及共享 AaAT 行为的实现必须从 Git 根目录执行 `python ai2apps/tests/run_aaat_boundaries.py`，并完成相关 owner 测试；不得弱化边界规则。实际实现开始时更新 Desktop 下一发布 ledger；本轮仅完善提案，不声称已激活或验收新行为。
