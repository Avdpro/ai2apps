# Bot 单层任务委派 C2 实施说明

2026-11-04。总体设计见 [Bot 通信与任务协作](bot-communication-and-collaboration-v1.md)，文本咨询保留 [C1](bot-communication-c1-implementation.md) 路径。C2 面向同一 Local、同一用户的立即单层子任务；定时/Hook 委派、长期协作授权和多层委派仍待后续实施。

## 用户流程

用户可以让主 Bot 请另一个自有 Bot 执行一部分工作，再由主 Bot 汇总。主 Bot 在自己的执行任务中通过 `messager.bot.directory` 解析稳定接收者，通过 `messager.bot.delegate` 提出精确标题与执行要求。委派提案保存后，原执行回合在已提交的 Tool 检查点结束，原 Task-Session 显示“等待协作”；实际执行槽位释放，用户既能聊天，也能让同一个 Bot 执行独立任务。

原发起 Bot 对话展示接收者、任务要求、执行模型和允许的能力。用户批准前不创建子任务，也不调用接收模型。批准后由实际接收 Bot 创建自己的 Todo 托管任务、Task-Session 与执行 Session，并进入它自己的串行队列。重复批准和恢复沿用原请求/任务/Run，不能创建第二次执行。

子任务缺参数或需要用户批准时，默认在原发起对话中显示实际执行 Bot、当前任务、具体问题及原交互。用户主动打开接收 Bot 对话时，也能处理同一个 Run/interaction。任一处提交后，两处轮询同一状态，不产生两份批准。特殊操作的确认显示所属 App 信息，只允许批准本次操作，不提供会话、Run 或长期授权扩展。

子任务成功后，宿主保存标准多模态结果与受控产物引用，将结果提供给父任务；父任务在同一 Task-Session、同一执行 Session 中排队启动新的执行回合。新回合带当前协作结果的冻结上下文，原模型/Tool 步骤和审计仍保留，不重新执行旧 Run。回执明确区分已提案、等待审阅、子任务已接受、等待输入、子任务完成及原任务继续。

## 权限与资料边界

C2 准入权限取发起 Bot 与接收 Bot 当前 App/Mini-App 权限的交集，并冻结 Provider 版本、Tool 目录版本、双方授权版本、接收方身份和审阅摘要。接收 Bot 的独有写权限不会被发起者借用；一份委派确认不改变任一 Bot 的长期权限。需要更大访问范围时，应先由用户在相应 Bot 的 App 访问设置中配置，再重新审阅任务。

普通已授权操作按声明执行，付款、敏感操作或 owner 强制确认仍走实际接收 Run 的原交互，审批范围限制为 once。回答资料不授予 App 权限。执行与恢复继续检查双方权限、Provider 版本、原会话和父任务停止状态；撤权、Bot 清理或取消会停止相关子任务与自动恢复。

首批只传用户审阅过的任务文字，不自动转移主对话、接收方私有记忆或附件。接收执行上下文使用被冻结的接收方身份职责，不导入其主对话历史。子任务新产生的、可验证的标准 artifact 由现有素材绑定与复制流程带回父会话；不接受任意文件路径或外部 URL 作为共享授权。

子任务不导出委派、咨询、配置或创建新任务的控制能力，不能再次委派。每个原始目标最多八项委派；相同根目标下对同一接收者的相同执行要求返回原请求，不重新执行。每用户最多十个等待/执行中的委派。子任务和父任务恢复回合分别限制为 24 步、600 秒及 64000 个模型 token；现有模型用量和账户规则继续生效，不能把 token 上限当成价格承诺。

## 执行与存储

`messager/delegation.py` 拥有提案、审阅、父子关系、原对话回接和恢复。`messager_bot_delegations` 保存双方 Bot、原会话/Run、父 job、不可变要求/权限摘要、子任务准入来源与 job、恢复来源与 job。实际执行状态仍来自原 Todo/Agent Run；“等待协作”是逻辑任务投影，不伪造另一个活动 Agent Run。

接收子任务和父任务后续回合都使用现有 `BotDialogue.enqueue`、Todo owner adapter、串行 lane 和受控 App Chat。内部准入 Run 由无工具的宿主执行器完成，不冒充用户新输入，也不绕过 AgentRun 状态机。子任务使用独立接收方 Task-Session；父任务后续回合关联原逻辑会话。准入记录、任务创建键与启动键稳定，跨库窗口按原 Todo 幂等机制恢复。

实际 Todo 状态回调与可恢复的系统观察任务都可推动协调，二者按持久关系幂等处理。子任务完成不依赖浏览器页面，也不因系统观察槽位排队而失去父任务恢复信号。父回合仍未终态时只保存结果，不能同时启动竞争续跑。后续回合经原 lane 竞争，其他正在运行的父 Bot 任务不会被打断。

App Chat 新增两项与业务身份无关的可信 owner 扩展：

- `execution_checkpoint(binding, context)`：仅在已提交步骤边界调用，允许 owner 返回 CompleteAction 结束当前回合，或返回 None 继续原执行。不得返回 Tool/模型调用或跳过当前 owner 执行授权；逻辑等待与恢复留在 owner。
- `approval_scopes(scope)`：只能收窄既有审批范围，不能从 once/run 扩大为 session/agent/app。C2 子任务限定 once，普通 Bot 的原范围保持不变。

通用执行器不识别 Bot 名称、业务 Tool 或 App ID。跨两个无关 Provider 的回归验证检查点结束回合、零额外模型调用与审批范围收窄；完整 AaAT 边界门禁覆盖新的共享扩展。Task-Session 摘要同时限制为只接受当前最后回合，防旧回合晚到的完成回执覆盖新结果。

## 取消与失败

拒绝、审阅过期、子任务失败/取消/结果不确定、双方撤权或原会话失效都会停止协作，父任务不自动重跑、不换 Bot/Tool 尝试同一效果。已发生的操作与产物保留，不声称已经回滚。用户可以查看原子任务记录，并明确发起新的后续工作。

停止父任务会传播至其独立子任务；停止子任务会结束对应等待关系。已经成功恢复的历史委派不再通过旧取消入口改写结果，父任务当前执行可通过原任务停止入口处理。

等待协作期间，原任务禁止归档；要修改这次已提交委派，首批要求先取消原协作并说明新要求。普通对话和独立新任务不受影响。定时计划修改不走 C2，需要后续后台委派计划审阅。

## 接口与验证

新增 AaAT：`messager.bot.delegate`。Local desktop 通过原 Bot `/work` 的 `delegations` 读取卡片，通过 `/messager/bots/{bot_id}/delegations/{ref}/decisions/approve|reject` 审阅，通过同请求的 `/cancel` 停止。状态变更要求既有 Local desktop 同源检查与 actor/Bot/请求归属；接收 Bot 的界面不能替代原发起会话批准初始委派。

验收使用真实 SQLite、Todo、Agent Runtime、API 和可控模型。覆盖父任务释放 lane、同 Bot 独立任务、接收者真实 Tool 调用、双方同一审批、一次性审批、拒绝/取消/撤权、权限交集、准入故障窗口、重复批准/恢复、原 Session 后续回合及当前上下文。前端验证初始审阅只在发起会话可用。夹具验证与真实付费模型/外部效果验收分别记录；本轮不自动执行用户付费绘图或批准敏感操作。

验收记录：[C2 收据](acceptance/bot-delegation-c2-20261104/README.md)。完整 AaAT 架构与行为门禁 1054 项通过（645.87 秒，退出 0），Bot 与共享表单前端 76 项通过。固定 App-Dev 已通过标准 Helper 空闲检查加载，并核对源码绑定、实际导入路径、持久表、接口和页面资源；原生 Messager 打开正常。新委派链路使用可控模型夹具验证，没有执行真实付费委派或用户敏感审批。

### 子任务记忆回传扩展（2026-11-04）

委派子任务增加 `messager.memory.return` owner 控制：成功交付时投递有证据的候选到直接上级，用户审阅后由独立记忆维护任务保存。它不带来继续委派权限，也不扩大双方 App Access。逐级来源、撤回、资源和去重边界见 [委派记忆回传 v1](bot-memory-delegation-returns-v1.md)。

### 即时委派在消息流中的展示

待批准时只显示执行 Bot、子任务标题、授权影响和操作按钮；完整指令、能力范围与限额收在默认折叠的详情中。批准后改为默认折叠的协作详情，停止协作入口在详情内；同一阶段的后台刷新保留用户手动展开状态。子任务排队和实际开始是不同状态：原对话在工作 Run 首次开始后收到一条独立、去重的文本通知。通知不授予能力，也不改变子任务的排队、预算或审批回接。
