# 新任务的稳定 Context 引用与连续执行验收

## 范围与所有权

Task owner 在创建新的 App Chat worker Session 时选择 `stable_context_history`，Session metadata 固定为 `agent_context_history=stable-references/v1`。普通 Bot 即时任务与 Bot 管理的系统 Task 启用；重开已有 Session 不补标记，不重写已有 Task、Message、RunStep。共享 Agent 不识别业务 Tool、App 或 Bot 名称。

## 稳定前缀

沿用按当前可见性验证后的工具目录与上次排序。新任务保留每 Run 的初始 UI 和 discovery 数据快照，置于当时的用户请求前；续接时按原位置回放，最新快照在新的用户请求前追加。旧观测只作为历史数据，不替代本轮权限和 Provider/version 复核。授权和工具 Schema 均使用当前定义，不缓存旧权限。

工具调用终态首次进入下一模型请求时，保存其模型可见 assistant/tool Message 投影。后续 Run 使用同一投影，避免当前 Run 已省略正文、下一 Run 又恢复全文或重新生成不同省略引用。原始执行参数和结果始终保存在 RunStep，不受显示投影影响。

完整失败回合和模型可见错误保留；不实现最近三轮滑动窗口，不删除失败调用，不每轮总结历史。原有达到上下文上限后的显式压缩机制仍独立存在。

## 大参数与结果

保留结构、短字段、资源标识。长字符串与 DataURL 使用确定性的路径、长度、SHA-256、短预览和原文读取入口。成功结果继续采用同一有界结果引用，保留 owner 的结果解释投影。首次显示后固定，不因经过的轮数再次裁剪。

`agent.read_tool_result` 对新策略 Session 支持读取同一 Session 的既有 completed/failed Run 内 Tool 输入、completed Tool 输出。跨 Session、未终结 Run、失败输出、不可用步骤均拒绝；旧策略仍限本 Run。并非文件系统访问或跨 Task 通用读取授权。调用前声明复核失败等未记录原始 Tool 入参的回合保留原模型调用，不伪造可读引用。

## 验证

确定性测试使用真实 Runtime、SQLite、调度器与两个任意 Provider 身份，验证投影重启恢复、跨 Run 原文读取、跨 Session 拒绝、原始参数/结果不变、旧 Session 不迁移。模型响应为夹具；实测连续任务与 Provider usage 单独记录，不能混为一项收益。

Dev 的基线和优化后任务读取同一个专用合成文档，故意请求一次不存在的 ID 后按真实错误纠正，再读取省略正文中的三行。使用 DeepSeek BYOK；usage 可观察 Token 与缓存命中，但没有实收金额，不能将估算当作账单。模型自主规划次数与历史长度须记录，不能直接把不同工作量的总量当成同条件节省比例。

## 实际连续 Task 验收结果

使用 Dev 专用验收 Bot、同一份 13,275 字符的合成文档，完成旧策略 A 与新建稳定引用任务 C 的连续执行。各组续接都先且仅一次读取不存在的条目，收到真实错误后使用正确 ID，分页读取 row 060–062 并核对 `MIDDLE-CHECK=ORBIT-7291`。两组均完成；C 的最终模型请求仍保留失败调用和明确错误，没有删除错误回合。没有向其它用户发送消息或重放用户任务。

| 观察值 | 旧策略 A 续接 | 新任务 C 续接 |
|---|---:|---:|
| 首轮输入 Token | 20,731 | 27,707 |
| 首轮缓存命中 Token | 13,952 | 18,432 |
| 首轮命中率 | 67.30% | 66.53% |
| 首轮未缓存输入 Token | 6,779 | 9,275 |
| 本 Run 模型调用次数 | 4 | 4 |
| 本 Run 累计输入 Token | 87,212 | 123,356 |
| 本 Run 累计命中 Token | 78,464 | 108,288 |
| 本 Run 累计未缓存输入 Token | 8,748 | 15,068 |
| 本 Run 输出 Token | 963 | 749 |

**这组真实 Task 没有证明成本下降，不能宣布缓存命中率提升。** 自主规划的读取范围、历史和上下文规模不同；输入/输出、缓存/未缓存价格也不同，因此这些计数不能当成同条件账单节省比例。BYOK 没有返回实收金额，本验收不声称金额收益。

C 续接首轮工具目录的 8 项声明与上一 Run 末次请求完全一致；上一请求的全部 **42 条消息按完整原顺序成为下一请求的精确前缀**，包括中间追加的 discovery 观测。原始字段、错误回合和读取入口没有因续接被重写。Provider 实际只命中 18,432 Token，说明正确前缀是必要条件，并不保证 Provider 已缓存全部前缀。

新增尾部有四条消息：上次最终答复、新 UI 快照、新 discovery 观测、本次用户请求。其中 UI 快照约 **9,318 字符**，discovery 约 **4,596 字符**。全量 owner 状态随新 Run 再次进入上下文，是剩余成本的明确来源；保留原位置的历史观测也比旧策略占用更多输入。后续应评估新增快照的通用增量表达与按需详情读取；应只改变新追加的数据表达，不能为了数字好看删除错误历史或每轮改写已发送前缀。当前实现没有启用这一额外机制。

初版真实 B 验收暴露了两处问题：中间追加观测未按原位置恢复，以及 Bot 队列回执被重复导入。最终代码已修正；保留 `optimized-v1.json` 作为调查记录，不将其列为收益证据。

## 新增状态快照的无损增量（2026-11-08）

新策略 Session 的 UI/owner 快照首次发送完整值；下一 Run 如能在模型消息里逐一找到上一快照及全部增量依赖，就只追加结构化变化。记录基准 Run、key/index 路径和 set/remove/splice 操作；未提及字段保持原值。数组头尾未变化的内容不重复传入，等长数组可只更新内部变化字段。若增量反而更长，则发送完整值。

完整源快照另外保存到 Session 事件，供下一 Run 比较；模型可见消息首次生成后固定，不根据后续状态或轮数改写。依赖链中任一消息被显式 Context 压缩、移除或没有进入实际请求，立即回退完整快照，不让模型引用不可见基准。旧策略 Session 保持原来的完整快照格式。

增量只优化非可信数据表达，不缓存授权、撤权、Provider 版本或业务结果，不改变 Bot 的排队、任务路由、失败恢复策略，不删除工具调用/错误。App/Mini-App 业务字段由 owner 原样提供，共享机制不识别特定业务名称。

D 新增 UI/owner 完整源快照等价表达为 10,837 字符，实际只追加 2,665 字符，减少 **75.4%**。它所依赖的首轮快照仍在历史原位置；前次最终请求的 **54 条消息构成续接首轮精确前缀**，8 项工具声明完全一致。第二轮最终请求仍保留一次真实失败 Tool 回合。撤回字段、数组插入、改值、重启、基准被压缩后的完整回退由两个任意 owner 的确定性测试验证。

实测首轮未缓存输入减少 **58.7%**，整个续接 Run 未缓存输入减少 **63.6%**，但**累计输入 Token 仅减少 0.7%**；输出略增加。缓存命中改善有实际 native usage 证据，不应把 63.6% 宣称为总 Token 或账单节省。前后规划和历史长度不同，首轮输入本身反而更长；缓存驻留/写入时机也由 Provider 决定。本次没有实收金额。

尝试安排额外同请求配对 Provider 计量，但自动审批拒绝额外完整上下文外发，因此该探测没有执行，也未绕过限制。结论仅依据上述真正连续执行和本地无损快照长度/精确前缀检查；不声称完成完全控制变量的价格对比。
