# 原生 Mobile：每个 App 独立 WebView 方案

日期：2026-10-18  
状态：设计备忘，待评估；未批准实施或部署。

## 决策与范围

未来考虑在原生 iOS 客户端中，为每个活跃的 App 实例保留独立 WKWebView。切换 App 只切换可见容器，保留页面、滚动位置、输入状态和该 App 的导航上下文。

**当前实现保持不变。** 不修改 Swift、Mobile Shell、Cloud 协议、权限、缓存数量或右滑行为；不构建、不重启、不发布。本方案不承诺已经解决 WebKit 的历史快照问题。

Safari 网页版继续使用现有 Mobile Shell 与 iframe 缓存。网页无法创建原生 WKWebView，不与原生方案强行统一容器实现。业务 UI、授权规则和 App 生命周期协议尽量共用。

## 背景和当前问题

当前原生客户端由 `ai2apps-ios/AI2Apps/WebSession.swift` 中的一个持久 WKWebView 承载 Mobile Shell。Shell 在 `ai2apps/web/static/js/mobile.js` 中维护 App iframe、最近使用缓存和共同的顶层浏览历史。

Mobile 已保留最近 4 个 App，缓存命中先显示、后台 focus 校验。情报中心在切回时保留文章详情，并通过补建历史层级维持“文章 → 频道文章列表 → 频道列表 → Home”的返回路径。

实际 iPhone 测试发现：补建历史时画面仍停在文章详情，右滑期间底层快照会显示这个画面，而动画结束后的目标页面正确。用户决定暂时接受这一视觉差异。

独立 WebView 可减少跨 App 共用历史带来的干扰，但**仅把 iframe 换成 WebView，不足以保证每层右滑快照正确**。App 内路由、历史条目和真实显示页面仍须一致。

## 建议结构

- 原生 Home / App 导航协调器：管理 App 切换、连接状态、活跃 App 和 WebView 池，不维护所有 App 内页面混合的浏览历史。
- 登录与连接容器：执行现有 Cloud 登录、Owner 交接及恢复流程。仅成功确认账户和目标设备后，允许 App 容器进入可用状态。
- 每 App 实例容器：承载专用的受限 Mobile Host 页面和业务内容，保留自己的历史、Bridge 和生命周期。一个实例最多一个活动容器。
- WebView 池：按最近使用顺序保留容器，处理后台暂停、内存压力、进程终止和淘汰恢复。

池键建议包含账户、安装/设备身份、App ID、App instance ID 和授权代次。不能只按 App ID 复用，更不能在 Dev/App-Dev、不同设备或账户之间复用。

### 优先采用轻量宿主适配

第一阶段不直接把任意 Package 页面提升为顶层可信页面。每个 WebView 加载专用的最小 Mobile Host，复用现有受限 App mount、资源通道和 context Bridge；Package 继续置于 sandbox iframe。

原生层无需接收全部业务数据。只有明确列入协议的导航和生命周期事件可以跨过原生边界。后续是否将特定可信内置 App 直接作为顶层文档，单独评估，不以“内置”或“原生客户端”替代授权。

## 导航和右滑

### App 之间

切换 App 时隐藏 A、显示 B，不在 A 的历史里插入 B，也不为 A 连续补建若干条虚构历史。回到 A 时显示原有文档和原有层级。

Home 是原生导航的根。App 内无可返回页面时，返回 Home；不得穿越到另一个 App 或登录交接页。交接页不能成为普通业务返回目标。

### App 内部

保留真实导航形成的历史，不在激活时重新合成。初始原型必须验证 SPA 的 pushState、iframe 内导航与 WebKit 返回列表如何协作，不能假定 WebView 自动理解 App 的业务层级。

每个 App 只能有一个返回动作的负责方：

1. 如果使用 WebKit 原生返回手势，应使历史条目对应实际显示过的页面，并验证动画结束前后状态一致。
2. 若 App 的虚拟页面无法可靠映射至 WebKit 历史，则采用原生协调的路由栈和返回转场；先完成明确的导航适配，不混用两套手势。
3. 编辑未保存、弹窗、输出预览等返回拦截必须遵循同一个路由协议。手势取消不得提前提交返回状态。

不要以临时逐层渲染、连续 pushState 的方式“制造”快照；这会带来闪烁、时序问题和切换延迟。WebKit 快照是否准确以真机验收为准，不能只由 JS 单元测试得出结论。

## 登录、会话与退出

同一账户连接范围内的可信容器，需要复用经过验证的 WebKit 登录环境，延续 HttpOnly Cookie 与 Owner 短租约；具体 websiteDataStore 生命周期和共享方式在原型阶段验证。独立 WebView 不等于独立 Cookie、网络或进程隔离。

- 不读取、导出或通过 JS Bridge 分发 Cloud Cookie、refresh proof、handoff 或通知 OAuth token。
- 沿用 Cloud 自动恢复协议；自然到期与主动退出保持区分。
- 多个容器同时遇到失效时，由一个恢复协调器处理，其他容器等待，避免同时创建交接或触发恢复循环。
- 恢复仅进行授权和必要的只读同步，绝不重放聊天、生成、发布、购买等业务写操作。
- 主动退出沿用 Local 持久撤销队列。原生立即遮挡/停止该连接的全部容器，等待可靠退出结果；不能由隐藏 App 再次自动登录。
- 账户/设备切换、权限撤销或授权代次变化时，失效旧池条目及原生页面快照，禁止误显上一账户内容。
- 不把清除共享网站数据当作关闭单个 App 的操作。退出账户与关闭 App 的语义必须分开。

## Bridge 与权限边界

每个容器使用自己的实例和挂载身份。宿主验证消息来源、frame、mount token、实例与当前连接，不能让 A 调用 B 的 Bridge。

保留 Package sandbox、现有 CSP、精确资源路由及受限 API。App URL 不能因装入原生 WebView 而获得 Local 管理权限；外部链接继续使用受控的外部打开策略。

需要原生消息处理器时，最小化方法集合，校验来源和主/子 frame，并在容器销毁时解除注册与引用。文件选择、下载、通知深链应显式路由到目标容器，不依赖“当前唯一 WebView”。

## 内存和生命周期

初步以最多 4 个热容器为试验上限，而非固定产品保证。实际数量根据真机内存、App 工作负载和后台行为确定；多个 WKWebView 不保证各自拥有独立系统进程。

- 活跃容器优先保留；最近使用排序淘汰后台容器。
- 后台发送生命周期通知，暂停不必要的动画、媒体播放和轮询；服务端任务不因 UI 被隐藏而自动取消。
- 未提交编辑、上传和实时交互应有可识别的保护状态；保护不能无限阻止内存回收，必要时提示保存或处理恢复。
- 淘汰前按既有协议保存允许持久化的轻量状态，例如页面 ID 和滚动位置。不保存秘密凭据、过期 mount 或完整私密页面快照。
- 再次打开被淘汰的 App 时，重新授权挂载并恢复可恢复的页面；不能承诺保留所有 DOM 状态。
- WebContent 进程被系统回收时，显示清晰恢复状态，按需重建；不得自动重新执行上一次业务动作。

## 分阶段验证

1. **技术原型**：只选择情报中心与 Chat，验证切换保留状态、各自历史、Cookie 环境和两层返回手势。使用隔离测试环境，不替换当前 Mobile Shell。
2. **导航协议**：明确 push/replace/back、交互式返回取消、未保存编辑、预览关闭和原生 Home 的职责。验证情报中心多级文章导航。
3. **容器池与恢复**：实现有界缓存、生命周期、进程终止、统一会话恢复及退出广播。覆盖长会话和断网场景。
4. **Package 兼容**：验证 sandbox、文件上传下载、Studio 输出、音视频播放及受限 Bridge，无新增隐式权限。
5. **小范围启用**：以原生功能开关控制，可回退至当前单 WebView Shell。Safari 保持现有实现。

若需要新增 Local Host 路由，必须先列清路由、方法、CSP 与鉴权要求。需要 Cloud 变更时，按仓库边界另写需求交由 Cloud 项目实施；本设计不授权增加公网白名单。

## 验收标准

- A 的文章详情 → B → A：文章、滚动位置和输入保持，缓存命中不重新加载文档。
- 真机右滑、取消右滑及按钮返回：预览快照与最终目标一致，无闪屏、重复返回或跨 App 历史穿透。
- 新开/深链进入、频道切换、Home 切换、连续快速切换均不会混淆路由和 mount。
- 最近 4 个 App 和超限淘汰场景可解释；记录切换耗时、内存峰值及实际进程回收情况，依原型基线确定性能门槛。
- 断网、切网、后台超过 30 分钟、超过 8 小时、Local 重启、多容器同时 401 均只触发受控恢复，不重放写请求。
- 主动退出、撤销、账户切换、设备切换后，所有相关可见/隐藏容器立即失效，不能露出旧账户数据。
- Safari 原有 Shell 不受影响，原生功能开关关闭后可回退。

## 当前待决事项

最小 Host 的具体 URL 与导航协议、原生 Home 是否逐步替代网页 Home、数据存储的账户隔离策略、App 未保存状态协议，以及 WKWebView 原生手势和 SPA 路由的可行边界，均在实施前通过原型确定。

此文仅记录方向；当前缓存和右滑快照行为继续保持现状。
