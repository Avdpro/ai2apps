# Dev Bot 工具载荷 Context 实测

验收日期：2026-11-08（Asia/Shanghai）。仅 Dev，端口 54972；App-Dev 未改动。使用真实 Messager Bot、知识库 AaAT、DeepSeek BYOK；测试正文为合成数据，非用户资料。没有重新执行用户既有任务，没有重启或完整 App 回归。

## 实际任务与续接

通过原生界面创建独立 Bot「Dev 验收：Context 载荷 A/B」。即时任务将 13,275 字符、120 行正文写入知识库，再读取实际 item_id 核对首尾标记与中部口令。后续对话续接同一任务，故意用不存在的 ID 做一次只读查询，再依据真实错误和上一轮回执改正 ID，通过原文 reader 取回被省略的 row 060～062。

结果：两次执行均 completed，保持同一任务会话和 worker session；只有一次写入、一次故意的查询失败。失败回执明确报告 `knowledge item not found`，模型随后使用实际 item_id 成功读取；原文 SHA-256 完全一致，中部三行逐字一致。界面完成结果也已查看。测试 Bot 和文档保留供复查。

| 实际执行阶段 | 输入 Token | 缓存命中 Token | 输出 Token | 总 Token |
|---|---:|---:|---:|---:|
| 保存、读回与校验 | 86,558 | 58,624 | 7,169 | 93,727 |

以上只计 worker 模型步骤，不含对话分流/规划；不能作为整个 Bot 全链路用量。这些是优化后执行的实际值，没有对应的完整优化前任务总量。

## 同轨迹输入 A/B

从首个真实任务固定两次写入后的模型请求。优化后使用实际的引用参数；优化前只将历史 assistant Tool call 的参数还原为持久化原始参数。其它消息、工具声明和结果保持一致，因此隔离的是本轮新增历史参数投影，不包括早已有的结果分页收益。

每组使用固定且等长的独立命名空间，避免实际任务已预热的缓存混入；每个请求发送两次，共 8 次真实 Provider 推理。Probe 输出限 8 Token、关闭 thinking；不执行返回的工具调用，真实写入只发生一次。使用 DeepSeek 原始 usage，`prompt_cache_hit_tokens` 与 `prompt_tokens_details.cached_tokens` 相符。Probe 与实际 worker 的推理设置不同，只比较 Probe 内成对输入，不能外推完整任务输出、推理量或费用。

| 请求 | 优化前输入 | 优化后输入 | 减少 | 重复请求缓存命中率：前 → 后 |
|---|---:|---:|---:|---:|
| 写入后下一轮（seq 6） | 18,820 | 16,939 | 1,881（10.00%） | 99.29% → 98.99% |
| 随后读取轮（seq 8） | 19,979 | 18,098 | 1,881（9.41%） | 99.30% → 99.02% |
| 合计 | 38,799 | 35,037 | 3,762（9.70%） | 99.30% → 99.00% |

首次 seq 6 两组均为零命中；追加 seq 8 后，前组命中 18,816/19,979，后组 16,896/18,098。说明历史参数投影后，连续请求仍可复用前缀。没有观察到缓存命中率提升；热请求未命中量合计反而从 273 到 349 Token，应保留分块/尾部差异的真实值，不能仅按总输入减少比例宣称费用下降。

## 判断与后续

本次真实任务证实：历史参数引用可减少重复输入，并保留续接、错误原因和按需原文读取。本案例两轮输入减少约 9.7%，不是先前大 DataURL 夹具的 97.96% 字节降幅。

缓存率基本维持，没有证明提高。实际首个任务后段为约 91%～98%；新 Run 的续接首轮仅 6,784/22,390（约 30.3%），后面恢复约 95%～99%。新 Run 的前缀重组、原始长用户请求，以及声明/历史结果的其它重复仍需分别测量优化。本次不修改这些机制，避免把不同收益混入 A/B。
