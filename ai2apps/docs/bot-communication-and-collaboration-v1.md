## 1 通信场景

| 场景 | 示例 | 协议要求 |
| --- | --- | --- |
| 专业咨询 | 写作 Bot 请腕表 Bot 核对型号与技术描述 | 关联问答、依据、置信限制；不能把建议当已执行结果 |
| 子任务委派 | 新闻 Bot 请翻译 Bot 翻译文章、设计 Bot 制作封面 | 接受或拒绝、排队、执行、结果、取消 |
| 资料和产物交换 | 发布 Bot 请求视频 Bot 提供视频与封面 | 摘要和受控资源引用，按接收方权限读取详情 |
| 多方审阅 | 文案交给事实核查 Bot 和品牌 Bot 分别审阅 | 独立意见、明确汇总者；不同意见不自动互相覆盖 |
| 顺序交接 | 视频生成后交给发布 Bot 准备草稿 | 接收方明确接受后转移后续责任；发布仍检查授权 |
| 进度订阅 | 用户助理关注视频任务的状态 | 关联原任务的进度、失败、待用户输入与完成回执 |
| 主动告知 | 腕表 Bot 发现重大新品后通知用户助理 | 业务事件与授权 Hook，不向所有 Bot 广播正文 |
| 修改和取消 | 用户改变主题，主 Bot 停止旧协作 | 请求版本、取消传播、已完成效果说明 |
| 共享资源协调 | 两个 Bot 同时修改文档 | owner 版本冲突检查和显式协调，不靠聊天实现锁 |
| 用户确认汇总 | 多个子任务缺少资料或需要审批 | 主 Bot 聚合展示，保留每个原始交互与批准身份 |

“给我一个封面建议”属于咨询；“生成封面”属于执行请求；“以后每天生成封面”属于长期计划。接收方必须按语义分别处理。咨询若需要工具或复杂处理，也创建接收 Bot 的任务；只有无需工具的简单答复可走短对话，二者共享总预算。

多 Bot 讨论组作为后续扩展：需主持者、明确参与者、发言与收敛预算，以及结束条件。首期不开放任意自动群聊。

## 2 系统组成与所有权

系统拥有的 Bot 通信服务负责身份验证、可见目录、消息持久化、投递、协作关系、回执与预算。Messager/Bot owner 负责是否咨询、是否承接、任务归属和用户反馈；Todo/Task-Session 负责实际执行生命周期；Event 服务负责事实和订阅。通信服务不建立另一套模型循环、任务执行状态或资源授权库。

Bot 通过可信声明的 AaAT 使用通信能力，UI 与 AaAT 复用同一业务服务。通用 General Agent 只消费声明和标准任务/交互协议，不按 Bot 名称、角色、业务 Tool 或 App ID 编写协作特例。其他 Bot 的消息、记忆摘要和工具结果都是业务数据，不能升级为可信系统指令或可执行回调。

首期只覆盖同一 Local 实例、同一用户拥有的 Bot。跨用户、跨设备、跨安装、Cloud 中继及第三方 Bot 身份均不在首期范围；需要 Cloud 行为时另写 Cloud 需求并交由对应项目实现。

## 3 通信对象与身份

| 对象 | 含义与边界 |
| --- | --- |
| 通信消息 | 一次不可变发送，含类型、正文/引用、发件与收件身份；编辑以新版本追加，保留历史 |
| 通信会话 | 有明确参与者的交流记录，不等于用户与 Bot 的主会话，也不等于执行 Session |
| 协作请求 | 目标、预期结果、范围、期限、预算、接受状态及关联任务；有唯一请求身份 |
| 协作关系 | 父 Task-Session、接收方 Task-Session、实际 Todo/Run、结果和取消关系的持久映射 |
| 资源引用 | owner、资源类型/ID、版本、来源与有效访问范围；引用本身不授予读取权 |
| 回执 | 已保存、已送达、已接受、排队、进度、结果或拒绝等事实，各自有独立含义 |

信封拟包含 `schema_version`、`message_id`、`conversation_id`、`request_id`、`in_reply_to`、类型、正文/引用、创建与到期时间，以及宿主持有的 actor/installation/Bot 身份和因果上下文。宿主从认证上下文生成发件身份、原 Task/Run、因果链和授权引用；模型只能提供目标选择与业务内容，不能自报 owner 或伪造来源。

接收者使用稳定 Bot ID；名称仅用于展示，重名或歧义时澄清。目录只返回当前用户可联系且允许发现的 Bot、声明的专长和可用状态，不暴露私有记忆、完整权限或历史。首期一次请求只面向一个接收 Bot；多方工作由宿主保存多个独立请求和同一个父协作关系。

## 4 消息类型与任务生命周期

协议至少区分 `question/answer`、`task_request/accepted/rejected`、`progress/result/failure`、`amend/cancel`、`handoff/ack`。业务事件由 Event 目录声明，不把任意消息正文变为新的事件类型。

1. 发起方提出目标、交付物、必要引用、截止时间与预算。宿主先验证通信与委派权限，再持久保存请求和待投递记录。
2. 接收方判断是否承接，明确返回接受、拒绝、需澄清或过期。传输送达不算接受；接受执行请求时幂等关联或创建自己的 Task-Session，再按自己的队列调度。
3. 实际执行继续使用接收 Bot 的 Todo/Run。协作请求只引用状态，不拥有另一份可独立改写的 running/completed 标记。咨询答复也保存来源和请求关系。
4. 子任务产出后，结果与回执持久提交；宿主按原关系唤醒父任务或向其提供可消费结果。父任务汇总实际结果，部分成功、拒绝和失败需分别说明。
5. 交接必须得到接收方接受；交接前发起方负责跟进。超时不能假称对方已接管，交接也不隐含授予外发、发布或付款权限。

用户输入的后续要求继续走现有 Task-Session 归属判断：未准入任务可按版本合并；执行中或等待审批的 Run 不原地改参数，把补充要求持久排为后续执行。已发送的协作请求不能用新正文暗改，须追加 amendment 并等待接收方确认实际生效范围。长期/周期协作修改创建可审阅的计划版本；只影响后续尚未准入的执行。

### 等待协作与执行槽位

现有 Bot 等待用户输入/审批仍占据串行槽位。拟新增的“等待协作”是独立等待原因：父执行先持久保存依赖、检查点和已提交效果，退出活动执行并释放槽位；子任务结果到达后，宿主通过同一逻辑任务的恢复流程重新竞争槽位。不能在旧 Run 尚在执行时启动竞争续跑，也不能为恢复重放已提交效果。

因此每个 Bot 同时仍只有一个活动执行，但可以有多个持久等待的协作任务；前台用户聊天始终独立。不得持有资源锁、执行租约或开放事务等待另一个 Bot。A 等待 B 时，B 可以向 A 发起有界澄清问答；不得再把原任务委派回 A。实现该等待协议前，不开放可能形成相互等待的多层委派。

## 5 权限与审批

通信权限与 App/Mini-App 访问权限分开。Bot 配置增加“Bot 协作”范围，按目标与方向明确允许咨询、接收咨询、委派、承接及后台协作。首次联系未授权对象时由用户审阅；用户也可主动配置固定协作关系。收到消息不自动授予主动通知、反向联系或长期协作权。

委派检查不仅是“接收 Bot 有权限”。有效执行范围由用户批准的协作范围、发起任务可委派的效果/资源范围、接收 Bot 的当前权限和准入快照，以及 owner 的操作约束共同限定。发起 Bot 缺少的权限不能借高权限 Bot 自动获得；用户可以明确批准一次经接收方执行的更大范围，此批准不反向扩大原 Bot 的长期 App 权限。

接收方任务在准入时冻结权限和协作策略版本，执行/恢复时检查撤权与 owner 当前约束。App 访问 不是委派授权，通信许可也不是资源共享许可。普通参数由 Bot 按可信声明与默认值补齐；必要资料、歧义、付费/敏感操作和声明要求的确认仍走原持久交互。

审批卡必须说明原用户目标、发起 Bot、实际执行 Bot、当前动作、拿不准的参数及原因。主 Bot 可聚合展示接收方的原交互，但用户回答/批准必须提交至原 actor、Bot、Task、Run、interaction 和版本；主 Bot 不得代签、复制批准或把聊天中的“好的”扩展成多个操作的授权。修改参数后按原协议重新审阅。

定时与 Hook 派生协作必须在后台委托中明确允许目标、动作、资源和预算，不能沿用一次前台聊天批准。Bot 删除/禁用、协作撤权或 Package 禁用后停止新投递与准入，并按已有撤权协议处理活动工作；保留必要审计。

## 6 资料共享与上下文

消息优先传必要摘要、结果结构和受控资源引用。接收方通过资源 owner 的 AaAT 读取详情，检查 actor、资源范围与版本，区分发生时的结果和当前状态。不能自动复制完整主对话、长期记忆、用户照片、Cookie、密钥或其他 Bot 的私有数据。

委派资源可采用明确的窄范围共享授权，必须绑定接收方、用途和期限；不支持授权共享的 owner 返回不可访问，由用户决定如何处理。撤权、删除、版本过期、结果部分可读均返回明确状态，不能改查其他对象替代。产物沿用标准多模态内容与 artifact 引用进入信息流，不向用户暴露内部执行指令或把 Python/JSON 结构直接当正文。

同一协作请求后续执行可复用接收方 Task-Session，复用上下文仍受权限、保留窗口和内容大小限制；不同 Bot 不共享 KV-Cache 或完整模型历史。摘要保留来源、版本、已确认事实与未决事项，不能把推测写成用户长期偏好。通信记录、协作索引和执行审计分别设置保留策略；删除展示记录不删除幂等凭据而触发旧请求重放。

## 7 Event Hook 与循环防护

请求/回复是有明确收件者的命令或数据；Event 是已经发生的事实。通信服务可在同事务 outbox 中发布经目录声明的接受、完成等事实，但回复原请求优先通过已保存的协作关系回接，不要求用户再配置一个 Hook。

送达、已读和普通进度只更新状态，默认不唤醒模型。需要另一个 Bot 自主处理时必须有明确通信策略或授权 Hook；同一个结果不能既由直接回接又由 Hook 重复创建任务。全局规则与运行监控放 Settings 的 Event/Hook，Bot 右栏只显示其参与关系和快捷入口。

沿用 Event 设计的可信 `cause_root_id` 和父因果关系，并增加协作请求与 Task/Run 引用。Hook 派生协作保留同一 root，不因换 Bot、AaAT、重启或异步 outbox 而重新获得预算。用户独立发起的新目标可建立新 root；针对旧任务的回答、审批与续接保留旧链，不能把回执当独立用户动作。

- 校验工作项依赖：允许同一Bot和祖先Bot处理独立子题；拒绝实际任务等待环及同一分支的原样重复分解。询问与结果回传消耗有界回合预算。
- 统一根预算：派生深度、激活数、咨询回合、消息数/大小、模型费用、效果次数和期限由宿主原子计量。沿用 Event/Hook 的限制，取各层最严格值，不新增独立的无限额度。
- 区分去重与防环：唯一请求阻止重复投递执行；新请求形成 A→B→A 的Bot身份复用不等于任务环，仍需任务等待图、重复工作和共享预算检查。冷却只限流，不证明无循环。
- 共享依赖图：入等待前检查互相等待；发现环时拒绝新依赖、返回原因并通知主 Bot，不让两个任务永久占用槽位。
- 身份或因果关系无法证明时拒绝自动有副作用协作；外部事件回声受窗口额度与暂停约束，不承诺识别任意外部循环。

## 8 投递恢复与并发

消息、请求、任务绑定与 outbox 在同库时同事务提交；跨库使用 owner outbox 和稳定幂等键。首期允许至少一次投递，接收方按请求 ID 和版本幂等接受；相同键不同内容报冲突。业务执行仍使用原 owner 的幂等协议，不宣称任意外部效果恰好一次。

结果入库、标记可消费与恢复通知可重送；父任务按结果身份/版本只消费一次。恢复使用持久 Task/Run 和受限租约，旧 Worker 不能覆盖新状态；重启和 UI 重挂载不创建新任务。超时记录结果未知时先查询原请求，不能自动找另一个 Bot 再做一次发送、删除或付款。

取消沿独立委派的子任务传播，接收方返回已停止、已完成或效果未知。已完成效果不回滚；补偿需要 owner 支持和相应授权。多方共享的一份咨询结果不能因单个订阅者离开而取消其他合法请求。共享资源写入使用 owner revision/冲突检查，冲突交回协调者处理，不以最后一个 Bot 的文字回复覆盖事实。

## 9 用户反馈与管理界面

### 用户批准和输入的沟通位置

默认在用户最初发起任务的 Bot 主对话中呈现全部待输入/审批，由主 Bot 统一跟进；多层委派仍回到这一会话。卡片显示实际提问/执行 Bot、原任务、当前动作、待补参数与原因，以及回复后继续的步骤。主 Bot 可整理说明，但不能替用户回答、改变原操作或签署批准。

展示位置不改变交互归属：回答和批准仍提交给实际执行 Bot 的原 Task、Run、interaction、参数及版本。用户主动在参与 Bot 的对话中处理时，两处显示同一条交互；任一处提交后另一处同步为已处理，不复制一份独立授权。参与 Bot 默认只显示关联等待状态和返回原对话入口，不重复通知。

定时或 Hook 协作在创建/审阅时绑定明确的用户沟通会话；不得由参与 Bot 临时选择窗口。原会话归档/删除、身份或授权失效时暂停需要用户参与的协作，提供安全的重新绑定审阅，不把问题发送到一个同名或自动新建的会话。多个问题可以合并呈现，但批准仍逐项保留原对象、操作和范围；用户资料回答只传给有必要且有授权的任务，不广播给所有参与 Bot。

主信息流提供简短、真实的反馈，例如“我请研究 Bot 核对资料，已排队；你可以继续聊天。”不能在对方接受前写成“它正在处理”。后台协作默认折叠，用户可展开查看参与 Bot、目标、状态、各轮动作、结果来源、费用/预算和失败原因。

需要用户回答时明确是哪项任务、哪个 Bot 在做什么、哪些参数拿不准以及回复后继续什么；多个问题可一起展示，批准仍逐项保留身份。失败、超时、取消、部分成功与交接未接受有不同文案。进度合并去重，不让 Bot 的礼貌回应互相触发通知。

右栏增加协作关系和当前依赖，可查看原 Task-Session、停止协作、撤销联系/委派权限。结果通知遵循原任务与 Bot 策略；主 Bot 汇总通知，参与 Bot 默认不再重复打扰用户，必要审批/失败仍按策略显示。新建、追加运行、追加等待、修改计划和委派都需明确回执。

## 10 拟议 AaAT 接口

以下仅为待评审接口语义，名称不是现有注册项。宿主身份、原 Task/Run、权限和因果字段均由可信上下文注入。

| 接口语义 | 输入要点 | 返回要点 |
| --- | --- | --- |
| 发现可协作 Bot | 专长条件、分页 | 可见 Bot 引用、声明专长、允许的联系模式 |
| 发送咨询 | 目标、问题、必要引用、期限 | 请求引用、真实接收状态 |
| 请求子任务 | 目标、目标说明、交付物、范围、预算 | 请求、Task-Session/排队或待审批引用 |
| 查询/读取协作 | 已授权请求、结果游标 | 原任务快照、结构化结果、受控引用 |
| 补充协作请求 | 原请求、预期版本、补充内容 | 合并、追加等待、需澄清或冲突回执 |
| 取消协作 | 原请求、预期版本、原因 | 停止状态、已发生效果与未决项 |
| 请求交接 | 接收方、任务目标、必要引用 | 待接受、已接受或拒绝，不隐含执行授权 |

订阅持续业务事实使用现有 Event/Hook 的注册与用户授权流程；读取状态不创建订阅。模型不直接调用内部投递、accept、回执写入或任意 Bot 冒名接口。具体 Schema、存储迁移与声明在实施阶段评审，权限模型先于开放执行入口。

## 11 分阶段实施与验收

| 阶段 | 范围 | 准入与验收 |
| --- | --- | --- |
| C1 通信基础 | 同实例同用户目录、显式联系授权、问答、持久投递与回执 | 身份防伪、不可见目标拒绝、重复投递、版本冲突、限额、重启；简单咨询不获得工具执行权 |
| C2 单层任务协作 | 子任务接受/拒绝、Todo/Task-Session 绑定、等待协作恢复、结果与取消回接 | 接收方权限冻结、禁止权限借道、每 Bot 单活动执行、聊天不中断、恢复零重复效果、原审批回接；完成后才开放自动工具协作 |
| C3 事件与长期协作 | 目录事件、Hook、计划版本、多方审阅和汇总 | 后台授权、root 预算、直接回接/Hook 去重、撤权、计划变更只影响下一次执行 |
| C4.1 有界多层委派 | 显式允许下级分工、持久依赖图、逐层结果回接 | 原入口逐次审批、任务等待图防环（C4.1.1允许同Bot独立子题）、共享预算、逐层权限收缩、停止与恢复；C3 固定后台计划不扩权 |
| C4 后续扩展 | 讨论组和动态协作；跨安装/跨用户另行评审 | 主持与结束、身份和资源共享协议；Cloud 需求单独交接 |

C1/C2 先验证“主 Bot 请另一个 Bot 完成一部分工作”：一个只读咨询和一个产物子任务；测试采用任意不同 Bot/Provider 身份，避免写死业务例子。必须覆盖拒绝、参数不完整、待批准、权限撤销、重复/延迟/乱序回执、进程崩溃、父取消与子完成竞态、同资源版本冲突、结果未知不自动重试，以及同名 Bot 不混淆。

首批 C1 使用逐请求授权，不保存长期联系关系。接收方只对经用户审阅的必要文字回答一次，不读取私有记忆或 App，也不创建需要工具的子任务；采用卡片展示的发起请求模型，尚不自动选择接收 Bot 的模型。咨询有一次模型回合、120 秒执行期限、1000 输出 token、每 Bot 最多 10 个待处理请求及每用户每天最多 20 个请求的上限。后续开放 C2 前必须接通原始审批双处呈现、协作等待恢复和委派权限，而不能把 C1 的确认当成这些能力的授权。

实施修改共享 Agentic/AaAT/交互协议时运行完整边界回归；对新增等待协议提供跨 owner 覆盖。端到端证据分别记录确定性夹具、真实模型、真实外部效果，不能以投递成功替代任务完成。文档阶段不改变现有执行槽位、权限和 UI 行为。
