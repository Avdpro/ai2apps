# Bot 事件与长期协作 C3

日期：2026-11-04。状态：首版已加载 App-Dev；完整边界回归1067项、前端15项通过，取消/配额及最终事件路径另有专项复核。模型与业务效果使用夹具，未执行真实付费任务。实现入口为 `messager/collaboration.py`。验收记录见 [C3 验收目录](acceptance/bot-collaboration-c3-20261104/receipt.json)。本阶段限定同一安装、同一用户、固定的 1–3 个其他 Bot；不开放递归委派、群聊讨论、跨用户或跨安装通信。

## 用户流程与接口

发起 Bot 通过 `messager.bot.directory` 解析真实参与者，通过 `messager.collaboration.propose` 准备计划。模型只能提出计划，不能批准。原 Bot 对话中的宿主卡片展示每个参与者和交付要求、模型、触发条件、后台权限交集、部分结果策略、有效期及共享预算。用户确认后才准入。

触发方式为立即单次、Todo 定时单次/重复计划，以及标准 Event/Hook。定时规则沿用 Todo 的时区、到期与执行协议。事件严格采用目录中已声明的类型、资源或已声明的 owned_collection、过滤条件及详情绑定；协作准入本身通过注册的 HookAction、冻结动作计划与真实批次收据执行，监控不会将其误标为只读观察；协作作为独立注册消费者 `ai2apps.messager.collaboration`，没有放宽原有只读 Bot 观察消费者。全局 Hook 仍由 Settings 的 Event/Hook 管理。

接口：

- `POST /messager/bots/{bot}/collaboration-plans/{plan}/decisions/{approve|reject}`：提交原卡片 `review_hash`；要求 Desktop owner、同源请求及原 Bot。
- `POST /messager/bots/{bot}/collaboration-plans/{plan}/pause`：停止后续触发及尚未完成的协作；保留已完成效果与审计。
- `GET /messager/bots/{bot}/work` 的 `collaboration_plans`：有界计划卡片；`delegations` 和原消息快照继续呈现实际子任务和原审批。

这些是所属 Messager 的接口，不是 General Agent 的业务分支。共享 AppChat、General、参数表单与结果渲染没有新增 Bot 专用逻辑。图片继续复用另一会话维护的既有显示组件。

## 计划版本

计划是不可变的已审阅快照。修改时提出新计划，填写明确的 `replaces_plan_id`；宿主冻结原版本的 `review_hash`，拒绝过期替换。确认后新准入使用新计划，旧计划进入 retiring，不再接受新执行，旧 Todo 不再生成后续到期槽位。已经创建协作批次的执行保留其旧快照和交互；它仍会检查权限撤销、有效期与特殊操作确认。

旧事件规则在已准入批次和 Hook 执行收尾后停用，收尾期间新投递不能通过旧计划准入。尚未形成批次的排队调度不获得继续启动旧版本的权利。明确“停用”与“替换”不同：停用会取消未完成工作，替换保留已经准入的批次。停用或过期后不得用普通聊天答复恢复；需要新的审阅。

## 执行与权限

宿主协调器不调用模型和业务工具，使用隐藏的系统执行 Session，不占用原 Bot 主对话，也不占其普通任务执行 lane。定时协调使用独立的 `messager-collaboration:{bot}` lane。每个参与者沿用 C2 的真实 Todo、Task-Session 与 AgentRun，在自己的 Bot lane 中串行执行。

计划明确冻结发起方及全部接收方的身份与后台权限；接收方有效能力只取双方交集。旧版前台专属授权不转成后台授权。新的 App 访问 授权按照现有 Bot App Access 契约生效，但协作计划仍需单独确认。不会自动共享原主对话、长期记忆、照片、文件或其他 Bot 的私有上下文。事件任务仅取得已批准的事件及精确 AaAT 详情。

普通参数由执行 Bot 根据用户目标和能力声明处理。付费、敏感、特殊声明和不明确的必要参数继续走实际接收者 Run 的原持久 Interaction，只允许当次批准。默认在发起 Bot 的主对话显示，双方查看的是同一 Run/Interaction，不复制授权，不为后台子任务授予长期 App 权限。身份、Provider 版本、权限 epoch、原会话归属、计划状态和原 Hook 状态都会在执行前再次核对。

## Event、因果与预算

新增目录事实：

- `messager.collaboration.accepted`：批次已持久准入，尚不代表模型开始或完成。
- `messager.collaboration.completed`：批次结束，status 区分 completed、partial、failed、cancelled。

事实 payload 仅含计划引用、状态、参与数量，不广播对话正文。`messager.collaboration.details` 按 actor 及原事件读取批次名称、当前状态、具名参与者状态与结果对话引用，区分发生时事实和当前状态；数据不授予权限。事实与批次更新同事务发布，发生键固定。

每次事件投递以 delivery ID、每次 Todo 执行以其 run ID 幂等准入。子任务以批次和参与者序号固定标识。直接回接只消费实际子任务结果，不另订一个 Hook 完成同一任务。宿主保存的原因果 root 和祖先链进入子任务工具调用作用域，并传到该作用域内发布的事件及协作汇总事实；同一计划在同一 root 只能准入一次。原 Hook 的深度/激活/重入限制继续适用。

一个 root 最多预留 48000 模型 tokens、36 次子任务工具调用；一个批次共享 600 秒期限，每个子任务最多 12 步。tokens 在准入时保守预留，不因失败退款后重跑；工具按原 invocation ID 原子去重计量，Gateway 与 Router 的重复检查不会双扣。事件触发还扣除原 Hook 的详情读取，并取原 Hook 调用上限与此处上限的较小值。后续协作不能换新请求键、Bot 或异步边界取得第二份同 root 模型预算。每个用户至多 5 个活动批次、30 个待审阅/活动计划。每计划滚动24小时最多24个新批次，事件批次至少间隔60秒；配额在准入事务内计量，失败或取消不退回。该上限不是货币费用预测。

异步业务 owner 必须在自己的队列、恢复和 outbox 中保存并恢复宿主 cause，才能证明其延后发布事件与原调用属于同一因果链；本阶段没有为所有 App 的私有异步队列增加通用推断。缺失这条证据的独立/外部事件不能被声称已证明无环，另由上述计划日配额、间隔和授权有效期限制。冷却不能代替因果防环；协作自身的准入/结束事实与标准 Hook 链保留原 root，不依赖这种兜底。

## 结果与失败

参与者独立取得同一份计划中各自的任务与已批准触发上下文，不把一方建议当成另一方的执行指令。首版采用宿主具名汇总，不增加一次不受控的模型总结；保留各方原始结果、明确失败和产物，用户可在原对话继续要求综合分析。

`all_success` 要求全部成功；否则整项未满足完成要求，但仍保留实际完成的结果。`allow_partial` 允许部分结果，必须标明哪一方未完成。不会覆盖分歧、伪造一致意见、自动重试未知效果、换 Bot 重做或回滚已完成操作。

重挂 UI、重复审阅和投递使用原收据。协调器准入间隙可按固定键恢复；已有实际 Run 被中断或失败时停止剩余批次并保留结果，不自动重放效果。到期、撤权、原对话归档和 Hook 停用会阻止新操作。用户必须重新审阅才能扩大范围或重新执行。

## 验证边界

测试使用真实 SQLite、Event/Hook、Todo、AgentRun、权限与持久交互，模型和业务效果为可控夹具。覆盖多方汇总、源/接收者后台权限、同一审批回接、特殊操作暂停、事件详情读取与回声防环、定时入口、部分失败策略、撤权和计划替换。前端验证只检查审阅与停用的显式请求，不模拟批准真实用户任务。实际模型费用、图片生成和外部通讯不在本次夹具验收中执行。
