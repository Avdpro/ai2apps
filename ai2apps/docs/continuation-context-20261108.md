# Bot 新 Run 续接 Context 精简

日期：2026-11-08。接续工具载荷实测，不引入最近 N 次调用窗口或模型摘要。

## 定位

对专用合成验收任务的实际第二 Run 首轮逐项检查：

- 同一 13,275 字符用户正文经主对话导入和 worker 提交进入两次。
- 主对话的排队/开始反馈被回灌到原 worker；最终答复又复制了一份，和 worker 本身的答复完全相同。
- 新 Run 工具 Schema 恢复后重新按名称排序，破坏上一 Run 逐步追加形成的工具顺序。当前 9 个定义名称本身没有重复。
- 新鲜 discovery observation 和 UI/任务快照位于稳定历史之前；时钟、任务状态或记忆变化会使历史前缀失效。
- 历史 app.describe 回执和当前工具定义有参数说明重叠，但回执还携带 owner、Provider/version、表单与参数契约等信息，不能整条删除。此次保留原回执和版本守卫，不以重复文字判断过期声明。

## 改动

1. Messager 任务 owner 不再复制本次已由 worker 精确提交的纯文本原用户消息；带附件/非纯文本消息继续原路径。已有持久记录不删除、不迁移。
2. 同任务续接不回灌 owner 明确标记的 bot_task_feedback。主对话结果只有在其文本 parts 与同一 worker Session 中原执行答复逐项完全一致且没有 artifacts 时才省略；编辑后的展示、素材以及其它有用内容保留。
3. 通用工具目录跨 Run 只恢复上一已完成执行的排列。每项 Schema 从本轮实时定义取，候选仍须先经过 Session 选择、当前可见性及 Provider 复核。撤权、升级、声明审阅和调用前守卫不变，不恢复旧 Schema 或旧授权。
4. App Chat 当前快照和 discovery 初始观测移到已有历史之后、本次请求之前。Run 内仍冻结原始观测、追加真正变化，不按年龄移动或删减调用链。新 Run 的动态观测仍是新数据，不谎称跨 Run 缓存完全稳定。

完整 Tool calls、失败原因、纠正后的调用、标准产物关系、原文 reader 回执及按需历史读取不删减。没有更改原始工具参数、执行结果或 Task 的重试/取消策略。共享层无业务名称分支。

## 验证

固定 AaAT 门禁相关选择 67 项通过、1,243 项未选（最终重跑 37.37s，exit 0），覆盖结构边界、任意 owner 快照顺序、跨 Run 目录排列/当前 Schema/可见性、真实 Runtime+SQLite 的任务串行续接及唯一请求/结果、附件传递、载荷原文读取和失败证据。模型/外部能力为夹具。首次新增测试使用了错误的类导入名，修正测试后重跑通过；不是运行代码失败。未运行完整 App 回归。

专用验收第二 Run 的冻结首轮请求做了真实 DeepSeek BYOK 成对推理，移除已定位的 4 个重复项并调整目录/快照顺序；无工具执行，输出固定 8 Token，thinking 关闭。结果：输入 22,371 → 19,456，减少 2,915（13.03%）；重复请求热命中 22,144/22,371（98.99%）→ 19,200/19,456（98.68%）。两组首次调用均为零缓存。这只证实该轨迹投影的输入收益，不是跨 Run 连续执行缓存收益或完整任务费用对比。

此反事实投影对应从修复后的新任务起产生的历史；已经写入的旧重复消息不自动清理。不能声称旧任务续接立即减少相同比例。缓存顺序改进由确定性契约测试验证，跨 Run 的真实增量命中收益尚需新的连续任务 Provider 样本。
